# Jev 三臂路由评测 v3.1：结果、修订与复核

可以接受本轮作为主题留出的合成语义挑战基准成绩。500 条真实 Jev 观测与供应商响应
一一对应；240 条 dev 选择阈值，260 条 test 按固定阈值评估。结果支持在这个基准内采用
置信度回退的价值，可用于简历中的离线评测成果，不能扩展成生产准确率或上线安全承诺。

## 主结果

test 为 260 条、13 个主题。实际服务模型全部为 typesafe/jev-1.14-20261014。

| 臂 | 正确数 | 准确率 | 复杂/不支持误分到快速路径 | 不支持请求未拒绝 |
| --- | ---: | ---: | ---: | ---: |
| 现有规则 | 130/260 | 50.0% | 26/130 | 26/52 |
| Jev | 247/260 | 95.0% | 13/130 | 0/52 |
| 混合，阈值 0.9 | 260/260 | 100% | 0/130 | 0/52 |

Jev 相对规则改善 130 条、退步 13 条，净提升 45 个百分点；混合改善 130 条、
退步 0 条，净提升 50 个百分点。两项主题级双侧精确置换检验均为
2/8192 = 0.000244140625，Holm 校正后均为 0.00048828125。

混合在 test 上采用 Jev 的 246/260 条输出，余下 14 条采用规则。每条仍需先调用 Jev
取得置信度，所以 94.6% 的输出采用覆盖率不是 API 调用节省率。
0.9 是模型提供的置信度分数门槛，不应解释为已经校准的 90% 正确概率。

既有、已暴露的历史参考集单独报告：混合在回归集为 107/107、困难集为 40/41，
没有使原规则正确的单条样例变错。这些参考集参与阈值选择约束，不是额外独立测试证据。

## 复核证据

- 500 个样例 ID 唯一，输入、标签、split 和来源与冻结数据逐字段相同。
- 500 个 Jev 结果均有对应 HTTP 200 响应；请求摘要与冻结问句、写入标志及提示一致。
- 501 份请求响应中，500 份为 200、1 份为 403；账本对应 501 次预留、500 次结算和 1 次注销。

- 根据原始观测重新计算 analysis.json，结果逐字段一致；8/8 已声明门禁通过。
- 没有新增模型调用，本次复核仅作离线计算及一次账户只读查询。
- 相关测试 77 项通过。

## 统计结论的范围

全部 500 条均由同一个助手设计并标注，为模板化合成数据，没有真实流量或独立人类标注。
每个主题包含相同的 20 种表达模板；dev/test 留出了主题，没有留出这些表达模板。
因此 13 个 test 主题不等于 13 种独立自然语言行为模式。

Jev 的主题聚类 bootstrap 区间为 [0.45, 0.45]，混合为 [0.50, 0.50]，
因为每个主题上的净差值完全相同。这个退化区间描述当前配平结构，不表达真实世界
不确定性。置换检验也依赖主题之间独立、组内两臂可交换等假设，共享模板限制这些假设。

0.000244 是此枚举设计下的精确 p 值，同时是 13 个非零主题差值时双侧检验的最小可达值。
不能因为碰到最小值就说它“不精确”，也不能把这个离散最小值视为生产泛化的强证据。
精确枚举与随机抽有限次排列估计 p 值的区别见
[SciPy 配对置换检验说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.permutation_test.html)。

Jev 危险降级的逐例 McNemar p 约 0.05325；按冻结方案仅是描述性补充，
不能宣称显著降低生产风险。混合的 0/130 也只是本基准观测，不能写成零风险保证。

## 错误集中在哪

test 中 Jev 的 13 个错误全部来自 ambiguous_subject，输入均为“工单 + 编号”，
例如“工单 4110”。记录主体是明确的，缺少的是用户要执行的任务；
报告中应称为“任务意图缺失”，而不是“主体指代不明”。

该类 Jev 为 0/13、规则为 13/13，错误置信度范围 0.45–0.64，低于冻结门槛 0.9，
所以混合回退到规则并纠正错误。这证明本轮观测中两侧错误具有互补性。
13 条仍是同一模板的编号替换，不能据此断言 Jev 只有这一种系统性盲区。

negated_operation 的真实例子是“不要删除工单 4110，只查数据库连接配置删除历史记录的
操作手册”，不是“不要关闭 MFA”。它与真正删除请求分开标注，Jev 在这个模板上正确。
模板措辞、数据分布和模型提示的对齐是本轮成绩的条件。

## 后续优先级

1. 保留本报告、响应、原始冻结方案和修订链。为当前 v3.1a 源码归档；
   初版执行源码目前只有摘要，若能恢复应补存对应内容，不应伪造初版快照。
2. 下一次付费前修正重试记账：目前所有 403/429/5xx 都会注销预留，且理由固定写成
   “推理前拒绝”。HTTP 状态或缺少 usage 本身不足以证明零计费；
   5xx 或带用量的错误应保留未知预留或按用量结算。已确认推理前拒绝的地区门禁可单独处理。
   预算/权限类 403 不应统一视为可重试错误，429 应尊重 Retry-After。
   参考 [OpenRouter 错误说明](https://openrouter.ai/docs/api_reference/errors-and-debugging)。
3. 完善续跑：按每条成功响应持久化，并绑定样例摘要、提示、模型和响应记录；
   避免进程在十条检查点之间退出后，重复调用已结算但未进检查点的样例。
4. 独立收集一小批自然问法，特别是只给编号、上下文省略、错别字、否定和复合请求，
   冻结后一次评估原阈值，不用这批数据重新选阈值。优先验证跨表达模板鲁棒性。
5. 正式生产判断还需要独立标注、真实流量分布、权限约束、故障和负载验证；
   双人标注是增强标签可信度的方法之一，单独完成它不足以证明生产可用。

没有必要为优化这张已有成绩表而反复花钱重跑同一 500 条。下一笔 API 费用应投入独立
自然问法的验证，而不是继续调高这份模板基准的分数。
