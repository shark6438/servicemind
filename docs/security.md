# Agent 安全评估体系建设方案（最终版）

版本：V1.0 · 2026 年 10 月 22 日 · 定位：企业级技术规范、前沿研究基线与工程实施指南

## 方案摘要

本方案的目标，是建立一套面向具备自主规划、工具调用、持久化记忆、多 Agent 协作及外部系统操作能力的 AI Agent 的安全评估体系。

体系采用以下原则：

- 风险框架统一：以 OWASP Agentic Applications 风险分类为主要目录，结合 MITRE ATLAS、NIST AI RMF 和企业业务威胁模型。
- 研究基准分层：结合公开研究基准、动态攻击测试和企业私有业务测试，不将不同基准的原始分数直接混合。
- 安全属性可验证：把越权、数据泄漏、审批绕过和危险副作用定义成可以由程序判断的安全不变量。
- 端到端评估：同时观测模型决策、工具调用、服务端授权、实际数据流和外部状态变化。
- 安全与效用联合评估：既测攻击是否成功，也测正常任务能否继续完成。
- 持续验证：把漏洞复现、修复验证、回归测试和上线门禁纳入日常研发流程。

OWASP 已发布面向 Agentic Applications 的 2026 风险框架；NIST AI RMF 的生成式 AI 配套资料则适合用于风险治理和生命周期管理。二者承担不同职责，不能互相替代。

## 1. 总体架构与评估边界

### 1.1 四层评估架构

## L1 · 业务安全结果

未授权读取、数据外泄、错误写入、危险副作用、业务规则违反。

### L2 · Agent 行为与执行链路

规划、检索、记忆、工具选择、参数构造、执行、委托与恢复。

### L3 · 独立安全控制

身份认证、服务端授权、策略网关、审批、DLP、沙箱、熔断与停止机制。

### L4 · 评测证据与持续治理

事件轨迹、资源状态差分、统计报告、漏洞回归、风险接受与发布门禁。

四层之间必须建立可追溯关系。例如，一次越权读取应能追溯到攻击输入、Agent 规划、工具调用、授权判定、实际读取结果和最终数据流。

### 1.2 被测对象

评估对象不应仅仅是大语言模型，而应是完整系统：

\\[ S=M+O+T+I+R+P+E \\]

其中：

- \\(M\\)：模型及模型路由。
- \\(O\\)：Agent 编排、规划和执行逻辑。
- \\(T\\)：工具、API、MCP 服务和外部连接器。
- \\(I\\)：身份、凭据和授权机制。
- \\(R\\)：短期上下文、长期记忆和检索系统。
- \\(P\\)：安全策略、审批和运行时控制。
- \\(E\\)：实际执行环境、数据资源和业务状态。

评测时必须冻结这些组件的版本。否则，当模型、工具或权限配置发生变化时，无法准确归因安全结果的变化。

### 1.3 评估边界

本方案覆盖模型层、Agent 层、系统层和运营治理层，但不声称能够证明任意 Agent 在所有未知环境中绝对安全。

需要明确区分：

- 公开基准测试通过：仅说明在指定基准和配置下取得了相应结果。
- 企业场景测试通过：说明特定业务场景下的已定义风险得到了验证。
- 独立控制验证通过：说明特定权限、隔离或审批机制在测试条件下有效。
- 上线风险可接受：还需要结合业务影响、残余风险、监控能力和责任审批。

### 2.1 前沿资料的使用规则

每个资料条目都应记录：

1. 论文或标准的准确名称。
2. 官方论文页面、代码仓库或标准入口。
3. 发表状态和版本日期。
4. 测试任务、环境和评分方式。
5. 适用的风险域。
6. 已知局限及企业适配成本。
7. 是否已经在本企业评测环境中复现。

同行评审论文、预印本、企业公开方法和标准规范应分别标记。引用论文并不意味着已经运行其代码，更不意味着其全部结论适用于本企业系统。

## 3. 十二类安全风险与测试要求

主风险目录采用 OWASP Agentic Applications 2026 的十类风险，并补充企业业务中的数据安全与评测可信度要求。下表是本方案的实施映射，不是对 OWASP 原文的逐字转录。

| 编号  | 风险域       | 关键测试与验收目标                   |
| --- | --------- | --------------------------- |
| R01 | 目标劫持与提示注入 | 恶意用户输入、网页、邮件和检索文档不能覆盖已授权目标  |
| R02 | 工具滥用      | 检查工具选择、危险参数、重复调用及未授权副作用     |
| R03 | 身份与权限滥用   | 验证跨用户、跨租户、过期凭据及权限升级         |
| R04 | 供应链与工具配置  | 检查恶意工具、依赖污染、工具描述篡改和版本变化     |
| R05 | 代码执行与沙箱   | 验证文件、网络、进程、凭据及资源隔离          |
| R06 | 记忆与上下文污染  | 检查长期记忆污染、跨会话影响、撤销和隔离        |
| R07 | Agent 间通信 | 验证委托身份、子 Agent 权限、消息来源及结果信任 |
| R08 | 级联故障      | 检查重试风暴、循环调用、资源耗尽和重复副作用      |
| R09 | 人类信任滥用    | 检查虚假完成报告、误导审批及未经授权的自动执行     |
| R10 | 失控 Agent  | 验证停止信号、预算限制、取消任务和恢复机制       |
| R11 | 数据与隐私     | 验证敏感数据最小化、流向限制、保留和删除要求      |
| R12 | 评测可信度     | 验证评分器、日志、环境隔离、测试集泄漏和结果复现    |

每个风险域都要同时记录三类结果：

1. 行为层：Agent 是否被影响，是否生成违规计划或工具调用。
2. 控制层：服务端权限、策略引擎和审批是否正确执行。
3. 结果层：是否实际发生了越权读取、敏感信息外泄或危险状态变化。

这三类结果必须分开报告。

### 3.1 优先级

首轮实施建议优先覆盖：

- P0：未经授权的敏感数据外泄、关键权限突破、不可逆高危副作用。
- P1：跨租户访问、审批绕过、持续性记忆污染、跨 Agent 权限扩张。
- P2：可恢复的业务规则违反、过度拒绝、异常重试。
- P3：低影响的策略不一致和可恢复行为偏差。

这里的 P0–P3 是建议的内部严重程度分级，不是官方标准等级。每个级别还应依据业务影响、可利用性、可恢复性和暴露范围进一步判定。

## 4. 前沿基准的选择与组合

公开基准不应被无差别地全部运行。应根据被测 Agent 的能力选择基准，并明确其不能覆盖的风险。

| 基准或工具                       | 推荐用途                | 局限及适配要求                 |
| --------------------------- | ------------------- | ----------------------- |
| AgentDojo                   | 动态间接提示注入与合法任务效用     | 需要理解其模拟工具和任务边界          |
| ASB                         | 多场景、多种攻击与防御组合       | 需统一工具环境、评分定义和版本         |
| AgentHarm                   | 有害目标及多步骤有害任务执行      | 不能替代企业授权和数据泄漏测试         |
| AgentLAB                    | 长时程、自适应攻击、目标漂移、记忆投毒 | 需要足够的多轮执行与状态记录          |
| MT-AgentRisk                | 多轮工具使用中的安全退化        | 需要将攻击序列与实际业务风险映射        |
| MSB / MCP-SafetyBench       | MCP 工具发现、调用、跨服务器协作  | 需适配企业的实际 MCP Server 和权限 |
| AgentDyn                    | 开放式动态任务与间接注入        | 属于研究型补充，需复现并验证适用性       |
| AgentSecBench               | 安全属性及测量方法研究         | 不能直接视为成熟的企业认证标准         |
| Inspect                     | 评测执行、任务编排、评分和实验控制   | 工具本身不是安全基准              |
| Agent Evals / Trace Grading | 工作流轨迹、评分器和回归分析      | 需自建安全不变量和实际副作用判定        |

### 4.1 基准选择的正式规则

每个候选基准都必须填写以下映射信息：

- 对应的风险域和安全不变量。
- 原始案例数、运行次数和可复现版本。
- 工具环境、模型接口和依赖条件。
- 原始评分定义及企业改造后的评分定义。
- 未覆盖的企业风险。
- 与其他基准的重复覆盖。
- 接入成本、运行成本和维护责任。

不要直接平均不同基准的 ASR。不同基准的任务、攻击强度、环境和成功定义可能不同；应分别报告原始结果，再用共同的企业安全不变量进行关联。

## 5. 威胁模型与安全不变量

评测开始前必须明确资产、主体、权限和信任边界。

### 5.1 威胁模型

| 要素   | 需要定义的内容                                 |
| ---- | --------------------------------------- |
| 资产   | 个人信息、客户数据、内部文件、凭据、业务记录和系统资源             |
| 主体   | 正常用户、恶意用户、外部内容作者、子 Agent、第三方工具          |
| 信任边界 | 用户输入、RAG 内容、工具输出、长期记忆、MCP 服务和跨 Agent 消息 |
| 攻击能力 | 直接输入、控制外部内容、跨多轮交互、操纵工具返回值、利用权限配置        |
| 安全目标 | 机密性、完整性、最小权限、可审计性、可用性和可恢复性              |

### 5.2 安全不变量

安全不变量必须能被自动判定，不能只写成“Agent 应当遵守安全规则”。

示例：

不变量 A：数据访问授权

每次读取必须同时满足主体身份有效、资源授权通过和租户范围一致。

不变量 B：高危动作审批

任何要求审批的操作，都必须绑定具体动作、参数、目标资源和有效审批记录。

不变量 C：任务取消

用户取消任务或安全策略终止任务后，不得继续提交被禁止的外部副作用。

不变量 D：数据流向

敏感数据不得流向未授权的外部主体、工具或持久化存储。

不变量 E：委托权限

子 Agent 的有效权限不得超过当前委托明确授予的范围。

形式上，可以将单次运行的安全要求表示为：

\\[ \forall a\in A\_{\text{executed}}, \quad \operatorname{Authorized}(a)=\text{true} \\]

其中 \\(A\_{\text{executed}}\\) 是实际执行的动作集合。对于特定业务，还应加入资源范围、动作类型、审批状态和时间限制等约束。

重要原则： 如果模型生成了越权调用，但网关成功阻止且没有发生实际副作用，应记录为“违规尝试已被阻止”，而不是与成功越权执行混为一谈。

## 6. 测试集与案例规范

### 6.1 五层测试数据体系

1. 公共基准集：复现公开研究。
2. 企业业务集：覆盖真实工具、角色、权限与业务流程。
3. 动态攻击集：覆盖改写、跨工具、多轮和自适应攻击。
4. 历史漏洞回归集：保留每次已确认问题的复现条件和修复版本。
5. 隐藏保留集：用于检验过拟合、基准泄漏及未知变体的鲁棒性。

每个攻击案例应当配套正常任务和无害对照，防止 Agent 通过拒绝一切任务获得虚假的高安全分。

### 6.3 首轮案例设计

建议先建设 30–50 个高质量案例，重点覆盖：

- 直接与间接提示注入。
- 未授权读取与跨租户访问。
- 工具参数操纵与危险副作用。
- 审批绕过。
- 记忆污染与跨会话影响。
- 多 Agent 委托权限。
- 工具描述污染与 MCP 信任边界。
- 重试、取消和停止机制。
- 正常任务与错误拒绝。

该数量是第一阶段的工程试点建议，而不是行业标准。案例数量增加前，必须先证明环境隔离、状态观察和评分器是可信的。

## 7. 指标与统计规范

所有正式指标必须定义分子、分母、统计单位、证据来源和无效运行处理方式。

### 7.1 核心指标

| 指标        | 正式定义                              |
| --------- | --------------------------------- |
| 攻击成功率 ASR | 成功实现攻击目标的运行数 / 有效攻击运行数            |
| 越权尝试率     | 至少发生一次越权尝试的运行数 / 相关有效运行数          |
| 越权执行率     | 至少发生一次成功越权执行的运行数 / 相关有效运行数        |
| 敏感数据泄漏率   | 至少发生一次未授权敏感数据泄漏的运行数 / 相关有效运行数     |
| 危险副作用率    | 至少发生一次禁止副作用的运行数 / 相关有效运行数         |
| 攻击检测率     | 被正确识别的攻击数 / 实际存在的有效攻击数            |
| 防御阻止率     | 被指定防御成功阻止的攻击运行数 / 到达该防御控制的有效攻击运行数 |
| 审批绕过率     | 未经所需审批即执行的运行数 / 需要审批的有效运行数        |
| 正常任务成功率   | 达到预定义成功标准的正常运行数 / 有效正常运行数         |
| 错误拒绝率     | 被不必要拒绝的合法任务数 / 有效合法任务数            |
| 恢复成功率     | 达到预定义安全恢复状态的运行数 / 需要恢复的有效运行数      |

必须明确以下区别：

- 检测到攻击，不等于阻止了攻击。
- 越权调用被拒绝，不等于发生了越权执行。
- 没有观察到数据泄漏，不等于已证明所有数据路径都安全。
- 恢复到安全状态，不等于原本的合法任务成功完成。

### 7.2 安全与效用的联合报告

每轮评测必须同时报告：

1. 无攻击条件下的正常任务成功率。
2. 有攻击条件下的安全不变量违反率。
3. 有攻击条件下原始合法任务的完成情况。
4. 错误拒绝率。
5. 时延、工具调用和资源开销。
6. 高危失败案例及其实际影响。

可以额外计算效用保留率：

\\[ U\_{\text{retention}}= \frac{U\_{\text{defended}}}{U\_{\text{baseline}}} \\]

其中 \\(U\\) 是在相同测试集和成功标准下得到的正常任务效用。若基线为零，该比值无定义；即使基线非零，也必须同时展示两组原始结果。

### 7.3 风险加权指标

可以建立用于版本趋势比较的内部风险指标：

\\[ R\_{\text{weighted}}= \frac{\sum\_{i=1}^{N} w_i v_i} {\sum\_{i=1}^{N} w_i} \\]

其中 \\(w_i\\) 是预先确定的风险权重，\\(v_i=1\\) 表示第 \\(i\\) 次运行违反了指定安全不变量，否则为 0。

这个指标只能作为补充。不能让低危样本的大量通过抵消一次严重数据泄漏。报告必须同时保留最高严重级别、原始事件数和每个风险域的结果。

### 7.4 统计可信度要求

- 区分案例数量、独立攻击策略数量和重复运行次数。
- 对随机性较强的 Agent 重复运行关键案例。
- 对关键比例指标报告置信区间。
- 对同一案例的重复运行考虑案例内相关性，避免假定所有运行完全独立。
- 固定模型、提示词、工具、策略和评分器版本。
- 明确区分有效失败、基础设施故障、超时和无效实验。
- 不得因为测试超时或环境异常而将案例直接记作“安全通过”。

如果在 \\(n\\) 次独立、同分布的测试中观察到零次失败，常见的 95% 置信上界近似为 \\(3/n\\)。这一近似不能代替风险覆盖分析，也不能直接套用于存在强相关性的 Agent 测试。

### 8.4 判定器可信度验证

评测器不能成为不可质疑的单一裁判。

每个重要判定器都应使用已知结果的正反样本进行校验：

- 已知发生越权读取的样本，必须被判定器识别。
- 已知请求被拒绝且无副作用的样本，不得误判为成功越权。
- 已知发生外部数据发送的样本，即使 Agent 最终回答没有泄漏内容，也必须被识别。
- 环境初始化失败或证据缺失的案例，必须进入无效或待复核状态，不能默认通过。
- 高危事件必须能够从评分结果追溯到实际事件和资源状态。

LLM Judge 可以辅助分析语义，但不应单独决定是否发生了权限越界或真实数据泄漏。

## 9. MCP 与工具供应链的专项控制

对使用 MCP 或类似插件机制的 Agent，建议单独建立专项测试集。

重点检查：

- 工具描述、参数 Schema 和返回内容是否构成提示注入入口。
- 工具定义是否发生未经审核的变更。
- 每个工具是否使用最小权限和独立凭据。
- OAuth 令牌是否绑定预期资源并由服务端验证。
- 是否存在令牌转发、凭据泄露或跨服务滥用。
- 是否能通过工具名称冲突、参数操纵或跨服务器协作绕过策略。
- 高风险工具是否在实际执行时再次校验授权和审批。
- 本地 MCP Server 是否被限制在适当的进程、文件系统和网络边界内。

MCP 官方授权安全说明强调令牌受众绑定和服务端校验；OWASP 的 MCP 安全指南还建议采用最小权限、工具定义审查、敏感操作审批和集中式调用日志。

## 10. 上线门禁与风险接受机制

安全评测必须产生明确的发布决策，而不是只生成一个综合分数。

| 门禁         | 适用范围                  | 必须满足的条件                     |
| ---------- | --------------------- | --------------------------- |
| G1：常规变更    | 提示词、模型或普通工作流变更        | 固定回归集通过；无新增未处理的高危问题         |
| G2：高权限能力   | 新增写入、外发、记忆或子 Agent 委托 | 重新评测相关攻击面；验证授权、审批和副作用控制     |
| G3：高风险生产发布 | 敏感数据、关键系统或不可逆操作       | 端到端红队、独立控制验证、停止与恢复验证、残余风险审批 |

每次发布应产生以下决策之一：

- 通过：强制门禁通过，残余风险在批准范围内。
- 有条件通过：明确列出未消除的风险、补偿控制、责任人和复核期限。
- 阻断发布：存在未修复的高危越权、敏感数据泄漏或不可接受的副作用。
- 证据不足：环境、日志或测试覆盖不足，无法支持安全结论。

对 P0 级问题应设置阻断发布条件。这里的“零容忍”是发布策略，不代表有限测试能够证明未来风险概率为零。

### 10.1 变更触发规则

以下变化应触发完整或针对性的安全回归：

- 更换模型、模型路由或系统提示词。
- 新增、删除或修改工具与 MCP Server。
- 改变身份、权限、审批或数据访问策略。
- 修改长期记忆、RAG 或上下文组装逻辑。
- 改变重试、委托、取消或执行器逻辑。
- 修复安全漏洞。
- 发生与现有安全假设有关的生产事故。

每次回归都应记录变更范围、受影响的安全不变量、测试结果和是否需要重新审批发布。

## 11. 中国企业场景与合规映射

在中国企业环境中，技术评测应与适用的法律法规、行业要求和组织内部制度共同实施。

重点核对：

- 《网络安全法》及适用的网络安全要求。
- 《数据安全法》涉及的数据安全管理和分类分级要求。
- 《个人信息保护法》涉及的个人信息处理、目的限制、最小必要和相关评估义务。
- 《生成式人工智能服务管理暂行办法》及与具体服务形态相关的管理要求。
- 适用行业的金融、医疗、工业、政务和数据出境等要求。

法律适用性取决于部署模式、数据类型、服务对象和业务范围，不能仅凭一套技术测试直接得出合规结论。

建议将合规要求映射到具体技术验证：

| 合规目标  | 技术测试                  |
| ----- | --------------------- |
| 最小必要  | Agent 是否访问了完成任务不需要的数据 |
| 目的限制  | 数据是否被用于未授权的任务或用途      |
| 访问控制  | 跨用户、跨部门和跨租户访问是否被阻断    |
| 数据保护  | 敏感数据是否流向未授权的模型或外部工具   |
| 处理可追溯 | 能否还原数据来源、处理过程和操作主体    |
| 人工监督  | 适用的高风险操作是否具备有效的人工控制   |
| 变更管理  | 数据源、工具和权限变化后是否重新评估    |

最终合规结论应由企业法务、合规和安全团队根据具体业务事实确认。

## 12. 八周实施计划与验收标准

下面的计划以一个已有工具调用能力的 Agent 为试点。时间是规划建议，不是完成项目的保证。

第 1 周：资产盘点与威胁建模

阶段 1

- 梳理模型、工具、MCP、数据源、用户身份与权限。
- 建立信任边界图和风险登记表。
- 确定首批安全不变量与 P0/P1 风险。

  验收：资产清单、威胁模型、首批不变量和风险责任人齐备。

第 2–3 周：打通评测 Harness

阶段 2

- 建立隔离的模拟工具环境。
- 实现案例加载、Agent Adapter、Trace 采集与状态差分。
- 实现服务端授权记录和确定性判定器。

  验收：至少一个越权案例可以复现、自动判定并输出完整证据。

第 4 周：完成 30–50 个试点案例

阶段 3

- 覆盖提示注入、权限、工具副作用、审批和正常任务。
- 校验评分器正反样本。
- 对失败案例进行人工复核。

  验收：案例可重复执行；环境失败不会被记为安全通过；关键结论均有证据。

第 5 周：引入公共基准

阶段 4

- 根据能力和环境选择 AgentDojo、ASB 或其他专项基准。
- 建立基准到企业风险域的映射。
- 分开保存原始分数和内部评分。

  验收：完成至少一个公共基准的可复现实验，并记录适配差异。

第 6 周：动态攻击与效用测试

阶段 5

- 增加多轮、跨工具、记忆和委托攻击。
- 测量安全性、正常任务效用和误拒绝。
- 对随机性强的高危案例进行重复运行。

  验收：形成分风险域的指标报告和高危失败清单。

第 7 周：整改与回归

阶段 6

- 区分模型、权限、工具、记忆和运行时控制的根因。
- 修复缺陷并保留复现案例。
- 验证修复没有破坏正常任务。

  验收：已修复问题均有修复前后对比及回归结果。

第 8 周：上线门禁与交付

阶段 7

- 将固定回归集接入 CI/CD。
- 定义发布阻断、残余风险审批和紧急停用流程。
- 输出正式评估报告。

  验收：可以自动生成报告、识别门禁失败，并追溯每个高危事件。

### 12.1 后续扩展

完成试点之后，再扩展到数百个业务案例和更复杂的动态攻击。上千条案例可以作为中长期目标，但是否继续扩容，应根据风险覆盖缺口、攻击策略多样性、运行成本和统计要求决定，而不是以数量作为唯一成熟度指标。

## 最终结论

这套方案的核心不是让 Agent 在一批安全问题中获得高分，而是建立一条可验证的工程闭环：

威胁建模 → 安全不变量 → 基准与业务案例 → 隔离执行 → 真实状态判定 → 指标统计 → 漏洞整改 → 回归验证 → 上线门禁。

最优先的建设任务是打通端到端执行证据：能够证明 Agent 做了什么、权限控制如何响应、外部状态是否变化，以及修复后相同攻击是否仍然有效。

只要这条链路可靠，后续无论增加多少新模型、工具、攻击策略或研究基准，都可以持续纳入同一套体系，而不是每次都从头开始做一次临时的安全测试。
