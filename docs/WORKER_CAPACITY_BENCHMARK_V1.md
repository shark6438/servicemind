# Worker 容量与故障对照方法（v1）

本实验使用真实的任务创建 HTTP 接口、PostgreSQL RLS、RunWorker 和 RunQueue，
分别启动一个和两个独立 Worker 进程。身份依赖替换为固定测试主体，图执行体替换为固定异步等待与
一个幂等数据库效果，因此不调用模型服务、GLPI 或身份提供方。

原始报告入口为 [worker_capacity_v1.json](../evaluation/reports/worker_capacity_v1.json)，
其中包含冻结计划、逐请求响应时间、逐任务执行时间和积压采样的实验目录引用。
脚本为 [benchmark_worker_capacity.py](../scripts/benchmark_worker_capacity.py)。

## 正式观测结果

正式运行目录为
[run_20261105T152630Z](../evaluation/experiments/worker_capacity_v1/run_20261105T152630Z/report.json)。
Python 3.14.7、PostgreSQL 16.15、Linux 主机有 48 个逻辑 CPU；共享主机的其他进程负载不受本实验控制。
每臂独立运行一次，不提供跨运行置信区间。下面是该固定合成负载下的实测值：

| 指标 | 单 Worker | 双 Worker |
| --- | ---: | ---: |
| 接收并完成的任务 | 240 / 240 | 240 / 240 |
| 从首次提交到排空的吞吐 | 4.588 任务/秒 | 9.326 任务/秒 |
| 排队时间 P95 | 30.525 秒 | 5.096 秒 |
| API 返回 202 响应头 P95 | 20.115 ms | 18.410 ms |
| 最后一次提交后排空时间 | 32.389 秒 | 5.815 秒 |
| 5–10 秒完成量 | 22 | 48 |
| 10–15 秒完成量 | 24 | 48 |
| 15–20 秒完成量 | 22 | 46 |

增加一个 Worker 后，实测吞吐为原来的 **2.033 倍**，排队 P95 下降约 **83.3%**。
总执行槽由两个变成四个；这些结果描述该扩容配置，不能称为相同总资源下的优化。
两个容量臂均没有重复执行尝试，模拟效果数均为 240。

在突发租户隔离场景中，24 个突发任务与八个稳定任务全部完成，两个租户的观测最大图并发均为一。
突发租户排队 P95 为 9.199 秒，稳定租户为 0.079 秒；由于没有独占控制组，不据此声称稳定租户完全不受影响。

API 被 SIGKILL 后重启期间，已开始的任务仍由 Worker 完成，执行尝试和模拟效果均为一次。
API 不可用区间约 12.865 秒，包含当前环境中的 Python 模块导入与服务启动。
Worker 被 SIGKILL 后，存活者约在 2.993 秒后重新开始该任务，约在 5.121 秒后完成；
该任务有两次执行尝试和一次模拟数据库效果。恢复计时只有一个故障样本，测试租约为三秒。

## 对照设计

| 项目 | 单 Worker | 双 Worker |
| --- | --- | --- |
| 独立执行进程数 | 1 | 2 |
| 每个进程并发 | 2 | 2 |
| 总执行槽数 | 2 | 4 |
| 每租户跨进程上限 | 4 | 4 |
| 租户数 | 2，按请求索引交替分配 | 相同 |
| 请求负载 | 20 秒内每秒 12 个，共 240 个 | 相同 |
| 模拟模型等待 | 250 ms | 相同 |
| 模拟工具等待 | 两次，每次 50 ms | 相同 |

每组先运行四个预热任务，预热不计入结果。API 和 Worker 各自是操作系统子进程，
数据库为脚本专用的 Docker PostgreSQL，应用角色是 NOSUPERUSER NOBYPASSRLS。
API 使用真实 `POST /v1/servicemind/runs`，收到响应头时停止准入计时，然后读取任务编号。
API 返回 202 的时间不包含后台执行，也不包含完整响应体传输。

排队时间取数据库任务创建时间到首次 `benchmark.started` 事件时间，完成时间取
`run.succeeded` 事件时间。每组记录五秒完成量窗口和每秒积压数量，并等待全部任务排空。
总吞吐使用从首次提交到最后完成的完整区间，不以峰值窗口替代整组结果。

增加 Worker 同时增加了执行槽；这组实验可以说明受控负载下的扩展行为，不能说明
在相同总资源下吞吐提升，更不能推导生产模型或真实 GLPI 的吞吐。

## 租户隔离观测

使用两个 Worker、每进程并发一、每租户上限一。一个租户一次提交 24 个任务，另一个租户每
0.5 秒提交一个，共八个。分别报告排队 P95 和事件区间内最大执行并发。

该实验没有单独运行“正常租户独占环境”的控制组，因此不能量化突发租户造成的性能降幅，
也不能声称正常租户完全没有受到影响。它验证执行额度和该固定请求混合下的实际等待情况。

## 进程故障观测

API 故障场景：任务已经由 Worker 开始执行后，对 API 子进程发送 SIGKILL，再启动新的 API 进程。
通过数据库记录确认该任务的执行次数、效果数和是否在 API 不可用期间完成。

Worker 故障场景：任务已经写入开始事件，但尚未执行模拟数据库效果时，对持有任务的 Worker
发送 SIGKILL。存活的 Worker 在测试租约到期后重新领取任务，报告领取等待、完成等待、尝试次数和效果数。
测试租约是三秒；生产默认租约是一百二十秒，不能把测试接管时间当成生产恢复承诺。

模拟效果使用 `run_id` 唯一约束。当前故障注入位于效果之前，不覆盖“外部写入成功、状态尚未提交”
这一故障窗口，不能证明真实外部系统恰好执行一次。图执行体已替换，本实验也不验证 LangGraph
checkpoint 的实际恢复行为；项目中的其他测试负责这些边界。

## 复现与限制

在已安装项目依赖且能使用 Docker 的环境运行：

```bash
uv run python scripts/benchmark_worker_capacity.py run
```

默认自动创建并清理专用 PostgreSQL 容器，不接受外部数据库 URL，因此不会清空已有业务数据库。
若需要保留临时数据库进行复核，增加 `--keep-postgres`；脚本会输出容器名和监听端口，
测试用户名和密码均为脚本内公开的本地夹具值。

这是单主机、短时间、固定异步等待的合成实验。结果受共享主机负载、数据库连接和事件记录开销影响。
它不能替代真实请求分布、长期稳定性、模型质量、安全与业务写入的完整验证，也不预设扩容一定翻倍。
