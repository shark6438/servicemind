# Phase 4 RAG 质量根因分析与处置（2026-09-15）

> 本文回答一个问题：**TechQA 代理集上的检索指标为什么低，以及能改什么。**
> 全部数字来自本机真实语料与真实模型推理，无估算、无引用二手厂商数字。
> 凡属离线实验（未进发布报告）的数字，均标明其复现路径。

## 0. 结论摘要

1. **主要缺口在测量层，不在检索层。** 发布的代理报告测的是「top-30 候选池 + 纯重排」，
   而生产跑的是「top-100 候选池 + `0.85×重排分 + 0.15×minmax(检索分)` 融合」。
   在**同一协议**（生产重排窗口 8192）下换成生产口径，Recall@10 从 **0.7321 → 0.7643**、
   NDCG@10 从 **0.6077 → 0.6279**；旧 512 协议下的同一对比是 0.7286 → 0.7571、
   0.6087 → 0.6266（两个协议的完整对照见 §3.6）。
   即：**发布数字低报了自己**，代理与生产的口径不一致。
2. **检索本身的可改进空间已经很小，且瓶颈已定量定位。** 指标可分解为
   `R@10 = 池覆盖率 × 重排条件精度`。当前 0.7643 = 0.8714 × 0.877。
   两个因子都已被单独测量（§3.2–3.4），三条候选改动路径**没有一条同时改善召回与排序质量**。
3. **第三检索臂的召回增益未通过留出集确认；确认性验证已正式关闭（`CONFIRMATORY_FAIL`）。**
   开发集（280 可答，已反复分析）上曾测得 Recall@5 全体 **+2.86pt**、困难子集
   **+5.67pt**（CI 下界均 > 0）。预注册的**一次性留出集**（330 可答 + 180 不可能，
   从未参与选型）上，按冻结协议 §7 判定为 **`FAIL`**：Recall@5 全体 **+0.00pt**
   （两条 query 一得一失、精确抵消），困难子集 **+0.00pt**（71 条中 C1 把 6 条捞进
   top-10，但 **0 条**进 top-5）。**开发集的困难集 Recall@5 +5.67pt 没有复现。**
   两条独立理由：门禁一 1b 的基线**按构造恒为 0**（困难集定义为「C0 top-10 未命中」），
   其实质是一个 `rescue_rate@5` 端点——本轮**实际挽救数为 0**，在任何合理统计方法下都
   得不到证据（需 **≥ 4 次**挽救其置信下界才 > 0，见 §3.3 勘误），**但它并没有抬高门槛**；
   而门禁一 1a 完全不依赖该端点，同样 **Δ = +0.0000、LCB = −0.0091**。
   **即使把 1b 整个删除，收益门禁仍然失败。**
   与之相对，**门禁二三项全部通过且 LCB 均 > 0**（R@10 +1.52pt / MRR +1.35pt /
   NDCG +1.36pt）——第三臂的改善真实存在，但**主要发生在第 6–10 位**，不足以支持生产采纳。
   状态：`CONFIRMATORY_FAIL` / `PRODUCTION_NOT_APPROVED` / `SHADOW_NOT_AUTHORIZED` /
   `RESEARCH_ARCHIVED`。**不为该候选新建协议版本、也不采集新数据重试**（避免可选停止与
   重复抽样）。详见 §3.3 与 `evaluation/reports/phase4_holdout_prereg_2026-09-15.{json,md}`。
4. **§4.1 的弃答门禁在该代理集上不可能达标，且原因不在门禁本身。**
   弃答门禁的可达上限**恒等于候选池覆盖率**：即使假设一个完美检测器能判断「答案是否在池内」，
   在 depth-100 两路池下答案率上限也只有 **0.8714 < 0.90**。这是结构性约束，不是调阈值能解决的。
   （注意量纲：该门禁在代理集上本就不适用，这里说的是**即使施加**也无法达标；而 0.8714
   本身是 oracle 池覆盖率，不等于生产可实现的弃答率——生产 Reviewer 只看到最终 evidence。）
5. **测量层还有第二处口径错配：重排器序列窗口被写死为 512。** 生产继承 checkpoint
   自身的 8192 窗口，而评测只喂了 512。实测子块 p50 为 **1313 字符 / 417 token**，
   单独子块均未超过 512；真正被截断的是 query+passage 拼接对（抽样 **27.5%** 超过
   512 token）。已在生产窗口下全量重跑（v1.5，§3.6）：生产臂
   R@10 **0.7571 → 0.7643**、NDCG@10 **0.6266 → 0.6279**，新数字与独立的离线 TEI
   路径**十个数字逐位相同**（§2.7），v1.4 与离线之间悬置的 0.72pt 由此闭合。
   §4.1 各门禁在该代理集上仅给出点估计、均低于目标阈值（**不是**「门禁未通过」——
   该集合上门禁不适用，见 §3.6 判读 3），**结论方向不变**。

## 1. 证据边界（先说清楚什么不能声称）

- 标注是**源方 silver 单金标**（每条 query 一个相关文件），不是 ServiceMind 人工 qrels。
  因此所有数字只能作为**跨域鲁棒性代理**，不构成租户域内质量认证。
- 语料是 NVIDIA TechQA-RAG-Eval 公开技术支持语料（28,481 文档 / 96,293 passage），
  不是私有租户分布。
- 本文所有离线实验复用生产同款 BGE-M3（`5617a9f6…`）与 bge-reranker-v2-m3（`953dc6f6…`）
  权重与切块形状（420 token / 48 overlap），差异仅在候选池深度与融合公式。

## 2. 测量层缺陷与修复

### 2.1 双重 sigmoid：确实存在，但影响面与直觉相反

`scripts/evaluate_phase4_proxy_release.py` 对交叉编码器输出**又施加了一次 sigmoid**。
实测模型输出本已在 [0, 1]，二次 sigmoid 把所有分数压进 **(0.500, 0.7311]**。

影响需要分情形讨论，这里给出实测而非推断：

| 情形 | 是否受影响 | 实测证据 |
| --- | --- | --- |
| 纯重排排序 | **否** | 400/400 条 query 排序完全一致（单调变换不改排序） |
| 弃答指标 | **否** | 再叠一层 sigmoid 对照：阈值 0.730741→0.674968，而 answerable 0.3333 / impossible 0.7800 / 平衡准确率 0.5567 / ROC-AUC 0.6106 **全部逐位不变** |
| **生产融合（blend）** | **是** | 融合是 `0.85×重排分 + 0.15×minmax(检索分)`，重排分被**线性加权**，量纲直接带权重。同池对比：**278/280 条排序改变**，NDCG@10 0.6105→0.6204（**+0.0099**），配对自助 95% CI **[−0.0041, +0.0230] 跨零** |

结论：这是一个**真实的测量缺陷**（它让代理脚本的融合臂没有在测生产真正跑的东西），
且修复方向正确；但它**不是** RAG 效果不好的原因——净影响落在噪声内。
另外它带来一个操作性风险：已发布报告里的阈值 `0.730741` 处于**压缩量纲**，
若被直接当作生产阈值使用（生产重排分是真实概率 [0,1]）会几乎全部误判为「弃答」。

修复：抽出 `_reranker_probabilities()`，仅做值域校验（越界即抛错，防止交叉编码器
激活函数假设失效后静默错缩放），不再做任何重标定。回归守卫见
`tests/servicemind/test_phase4_proxy_release_script.py`。

### 2.2 弃答门禁原来只报了操作点，没报可分性上限

原实现只报校准阈值下的 answerable/impossible 两个率，读者无法区分
「阈值没调好」和「这个信号根本没有区分度」。现已补两个指标：

- `top_score_roc_auc`
- `best_case_balanced_accuracy`（遍历所有候选阈值的最优平衡准确率 = 任何阈值规则的上界）

本代理集实测：**ROC-AUC 0.6106、best-case 平衡准确率 0.6017**。
即该分数接近随机，**任何阈值都达不到 0.90/0.90**。见 §4 的进一步分析。

### 2.3 §4.1 的六项门禁被渲染成 PASS/FAIL 裁定

该门禁表是为**租户域内 release set** 定义的，却被用于裁决一个公开 silver 代理集。
现改为 `applicable: False / passed: None`，并在 reason 中写明为何不适用。
门禁阈值本身原样保留，可被引用，但不再冒充裁定。

### 2.4 §6.4「代理指标不得进一步退化」缺少可执行的基线

新增 `_proxy_regression()`：首次运行冻结
`evaluation/reports/phase4_proxy_regression_baseline.json`，此后每次比对，
容差 0.005；若数据集或模型 revision 变化则**拒绝比对**并抛出，除非显式
`--update-baseline`。状态写入报告的 `status` 字段
（`regression_baseline_created` / `regression_passed` / `regression_failed`）。

### 2.5 报告里仍然存在的限制（如实记录，未消除）

- 代理脚本的 BM25 臂**没有**模拟生产的 multi-query 改写臂
  （生产经 `SERVICEMIND_RAG_MULTI_QUERY=true` 为每条改写各跑一路 BM25，
  见 `src/servicemind/rag/opensearch.py:706`）。因此代理数字在该维度上**低估**生产。
- 稠密检索用精确 max-pooling，生产用 OpenSearch HNSW 近似再扩父块。
- 代理脚本的 RRF 融合在本地重算（`_rrf_scores`），并列时按 `doc_id` 字典序破并列，
  而生产的破并列由 OpenSearch 决定。该约定对**纯 RRF 臂**的名次有实质影响（§3.5 已量化：
  68/400 条 query 的 depth-30 候选**集合**由破并列决定），对**生产融合臂**无实质影响。
- **已消除**：脚本曾把重排器序列窗口写死为 512（生产为 checkpoint 自身的 8192），
  使所有旧代理数字都没有描述生产跑的重排器。该缺陷已修复并在生产窗口下全量重跑（§2.6、§3.6）。

### 2.6 重排器序列窗口被硬编码为 512，评测的不是生产跑的重排器

**缺陷。** 代理脚本的 `_reranker()` 原先把 `CrossEncoder(..., max_length=512)` 写死；
而生产 `BgeM3Reranker`（`src/servicemind/rag/models.py:174`）构造 `CrossEncoder` 时
**不传** `max_length`，因此继承 pinned checkpoint 的 tokenizer `model_max_length`。
本地快照实测：`tokenizer_config.json` 的 `model_max_length = 8192`、
`config.json` 的 `max_position_embeddings = 8194`（`num_labels` 为空，
架构 `XLMRobertaForSequenceClassification`）。

**一处必须先更正的数字。** 本节初稿写的是「96,293 条子块 p50 = 1313 BGE tokens，
按 512 截断意味着交叉编码器每条子块只看得到约 39% 的文本」。复测
（`measure_passage_lengths.py`，产物 `passage_lengths.json`）表明**这个数字是错的**：
1313 是**字符数**，不是 token 数。同一批子块在 BGE 与重排器两个 tokenizer 下长度一致：

| 输入 | p50 | p95 | max | 超过 512 的 |
| --- | ---: | ---: | ---: | ---: |
| 子块**字符**长度（96,293 条） | 1313 | 1738 | 2205 | — |
| 子块 **token** 长度（BGE / 重排器一致） | 417 | 418 | 427 | **0 / 96,293** |
| **query** token 长度（400 条） | 74 | 240 | 572 | — |
| **query + 子块 + 4 特殊符**（抽样 3,000 对） | 480 | 639 | 993 | **824 / 3,000 = 27.5%** |

**截断发生在哪一层，由 tokenize 口径决定。** `sentence_transformers` 的
`CrossEncoder(max_length=N)` 设的是 `tokenizer.model_max_length`，而 tokenize 的对象是
**拼接后的 pair**，不是单独的子块。所以：

- **单独子块一条都不会被 512 截断**（全部 ≤ 427 token）；
- 但 TechQA-RAG-Eval 的**问题本身很长**（p95 240、max 572 token），足以把 pair 顶过 512；
- 抽样 3,000 对里 **27.5% 超过 512**，被砍掉的是子块尾部（p95 仅超出约 127 token）。

即：窗口效应是**真问题**，但量级远小于初稿所述——不是「每段砍掉 61%」，而是
「约三成 pair 被砍掉尾部百余 token」。本节的定性（发布数字应当描述生产实际运行的重排器）
不受影响，受影响的只是理由。

**处置。** `_reranker()` 现在 `max_length` 默认 `0` = 不覆盖，即跟随 pinned checkpoint
自身的窗口（与生产一致），并**返回实际生效的窗口**；该值同时写入重排分数缓存的身份
哈希（`_reranker_scores` 的 `max_length` 字段）与报告的 `retrieval.reranker.max_length`
和 `max_length_source`。缓存身份写实际值而非常量是必要的：否则窗口变更后旧的 512
缓存会被静默复用。新增 `--reranker-max-length` 仅在需要显式复现旧协议时使用。

**但它不是已证明的质量杠杆——必须如实说明。** 在 40 条 query、13,461 对样本上把窗口
从 512 放宽到 8192：

| 窗口 | R@5 | R@10 | MRR@10 | NDCG@10 |
| --- | --- | --- | --- | --- |
| 512（旧协议） | 0.5250 | 0.5750 | **0.3936** | **0.4373** |
| 8192（生产口径） | 0.5250 | **0.6000** | 0.3781 | 0.4313 |

池内排序的 Spearman 相关均值 0.9716（最小 0.7606），rank-1 一致 35/40，
top-10 集合重合 0.9175；逐 doc 分数变化均值 −0.0028（p05 −0.0751、p95 +0.0561），
即分数整体平移极小但个体重排。结论是**互有胜负的平局**：R@10 多中标 1 条，
MRR@10 与 NDCG@10 反而略降。该样本仅 40 条 query，无力分辨 ±0.02 级别的差异，
因此**不能声称放宽窗口会提升质量**。

所以这条的定性是**协议一致性修正**（发布数字应当描述生产实际运行的重排器），
而不是一次调优。副产物：512 时代测得的代理数字**没有描述生产实际跑的重排器**；已在生产窗口下重跑替换
（§3.6）。注意 §3.6 里的「v1.4」是与 v1.5 同管线、只改窗口的归档重跑，与仓库里更早的
整篇文档粒度已发布版不是一回事。

> 样本说明：上表两列的绝对值（R@5 0.525）低于全量 280 条可答 query 的生产臂水平
> （v1.5 生产形态 R@5 0.6857，§3.6），因为样本取的是 `_select()` 输出的前 40 条可答 query，是一个
> 更难的子集。此处只用于**同集配对对比**，绝对值不可与全量指标并列引用。

### 2.7 两条重排打分路径：差异来自序列窗口，不是打分后端（层二离线实验的口径说明）

框架用**进程内** `sentence_transformers.CrossEncoder` 打分；层二的离线实验
（现归档于 `evaluation/experiments/phase4_third_arm_2026-09-15/`，含第三臂与重排器 A/B）
用的是 **TEI `/rerank` 服务**产出的
分数矩阵（`rerank_tei_v1.npy`）。生产两条路径都有（`BgeM3Reranker` 与 `TeiReranker`），
所以先要量清楚二者是否等价。

**先记下一个被推翻的中间结论。** 在窗口修正（§2.6）之前测得的差异是：池内排序
Spearman 均值 0.9821（p05 0.9101、最小 0.4912）、rank-1 一致 356/400、top-10 集合重合
0.9272（268/400 完全一致）、分数量纲均为 [0, 1]（p50 0.585 / 0.596）。当时把它读作
「两条打分路径不等价」。**这个归因是错的**：那次比对两侧的窗口并不相同——
`diagnose_scoring_paths.py` 读的是框架 **512 截断**的扁平缓存，而 TEI 服务端未设
`--max-input-length`（`deploy/glpi/compose.yaml` 的 `rag-reranker` 命令），用的是模型
自身的 **8192** 窗口。即：那次测量**混入了窗口变量**，而它给出的量级与受控的窗口实验
（§2.6：同为进程内、只改窗口，Spearman 0.9716、rank-1 35/40）几乎一致。

**修正后的测量（同池、同窗口）。** v1.5 在生产窗口 8192 下重跑后，两条路径在同一候选池
（400/400 条 query 的池集合完全相同）上逐 doc 比对：

| 对比量 | 512 期（窗口错配，结论已弃用） | 生产窗口 8192（同池同窗口） |
| --- | --- | --- |
| 池内排序 Spearman | 均值 0.9821、最小 0.4912 | **均值 0.9999、p05 0.9997、最小 0.9993** |
| rank-1 一致 | 356/400 | **399/400** |
| top-10 集合重合 | 0.9272 | **0.9950** |
| 逐 doc 分数差（进程内 − TEI） | −0.0028 | **−0.00083** |
| 完全同序（100 深）的 query | 0/400 | 0/400 |

**最强的一条证据是端到端的。** 把 v1.5 的 `production` 臂与离线 TEI 路径算出的
`blend100` 臂逐项对比，**五项指标与五个自助法 CI 边界共十个数字逐位相同**：

| 指标 | 离线 TEI 路径 | 框架进程内路径 | 95% CI（两者相同） |
| --- | ---: | ---: | --- |
| Recall@5 | 0.6857 | 0.6857 | [0.6286, 0.7393] |
| Recall@10 | 0.7643 | 0.7643 | [0.7143, 0.8143] |
| Recall@20 | 0.8071 | 0.8071 | [0.7571, 0.8500] |
| MRR@10 | 0.5848 | 0.5848 | [0.5332, 0.6358] |
| NDCG@10 | 0.6279 | 0.6279 | [0.5792, 0.6757] |

CI 边界也逐位相同，意味着**逐 query 的指标向量相同**，而不只是四舍五入后相等
（断言脚本 `compare_paths_at_production_window.py`，产物 `path_compare.json`）。
由此可以定性：**v1.4 与离线路径之间那 0.72pt 的差异（R@10 0.7571 vs 0.7643）
全部由窗口解释，与打分后端无关。**（此处的 v1.4 指 §3.6 的归档 512 重跑——与 v1.5
**同一条管线、只改窗口**；它不是仓库里更早的整篇文档粒度已发布版，两者不可混引，见 §3.6） 这也解释了为什么窗口修正后生产臂的五项指标
恰好落到离线路径的数值上（§3.6）。

仍然成立的口径边界（比原先收窄）：

1. 两条路径**并非逐位等价**：0/400 条 query 的完整 100 深排序相同，top-10 成员有约
   0.5% 的差异，逐 doc 分数存在 −0.0008 的系统性偏移。因此引用**绝对值**时以
   `evaluation/reports/` 的框架产物为准；离线矩阵用于 A/B 与漏斗分解。
2. 层二的 **A/B 对比仍然有效**：同一候选池、同一 query 集、两个交叉编码器在同一条
   打分路径下比较，变量被隔离。
3. 当前发布数字（v1.5）已被第三条独立路径验证：用框架自身的扁平重排缓存
   （`techqa_bge_reranker_<rev>_passages420_pool100.npy`，142,232 对）按同一池序重建
   逐 doc 分数后复算，`production` 五项指标**逐位相同**

## 3. 检索质量：把指标拆开看

### 3.1 分解式

```text
R@10 = 池覆盖率（金标是否在重排候选池内） × 重排条件精度（在池内时能否排进前 10）
```

280 条可答 query 实测：

| 候选池 | 覆盖率 | 说明 |
| --- | --- | --- |
| BM25 depth-100 单臂 | 0.7893 | |
| dense(BGE-M3) depth-100 单臂 | 0.8536 | |
| **RRF 两路 depth-100（= 生产候选池）** | **0.8714** | |
| RRF 三路 depth-100（嵌套构造，**已作废**） | 0.9250 | 见 §3.3 的方法更正 |
| **RRF 三路 depth-100（生产等权口径）** | **0.9143** | 第三臂 = Qwen3-Embedding-0.6B |

| 发布的 top-30 池 | 0.7929 | 发布口径 |

当前生产形态 `R@10 = 0.7643`，除以覆盖率 0.8714 得**重排条件精度 ≈ 0.877**。
两个因子都不是 1，因此两头都有空间，但下面两节说明各自为什么不值得动。

### 3.3 层二：第三检索臂（按生产真实融合口径重测）

**先更正一处方法缺陷。** 首轮层二把三路池构造成 `RRF(RRF(bm25, bge, k=200), qwen3)`，
即**嵌套融合**：内层两路融合后的排名被当成一个「臂」，再与 qwen3 做第二次 RRF。
生产不是这样跑的——`src/servicemind/rag/opensearch.py` 把 dense knn 与每条改写 BM25
放进同一个 OpenSearch `hybrid` 查询，由集群 RRF 管线以各自 rank 融合
（`pipeline: servicemind-rag-rrf-v1`，`rank_constant: 60`）。生产加第三稠密臂的等效式是

```text
1/(60 + rank_bm25) + 1/(60 + rank_bge) + 1/(60 + rank_qwen3)
```

三臂等权；而嵌套式里 qwen3 实际独占 50% 权重。两者不等价：

| 候选池（depth-100） | 覆盖率 |
| --- | --- |
| 两路（bm25 + BGE-M3） | 0.8714 |
| 三路·嵌套（首轮构造） | 0.9250 |
| **三路·真实等权（生产口径）** | **0.9143** |

嵌套池与真实池的 top-100 文档集合在 **400/400** 条 query 上都不同，因此首轮
「第三臂不满足门槛」的结论建立在生产不会运行的构造上，**已作废**。下表为真实口径
重测（同一 TEI 生产重排器，产物 `rerank_tei_true3.npy`，两路锚点由断言校验）：

| 2way + 纯重排 | 0.6821 | 0.7357 | 0.7786 | 0.5614 | 0.6036 |
| **2way + 融合（现役）** | 0.6857 | **0.7643** | 0.8071 | 0.5848 | 0.6279 |
| 三路真实 + RRF | 0.6714 | 0.7429 | 0.8071 | 0.5763 | 0.6160 |

按当时 `docs/PHASE4_EVALUATION_BASELINE_V1_2.md` §4.1 末句的字面规则（困难子集 NDCG@10
绝对提升 ≥ 2 个百分点**且** paired-bootstrap 95% CI 下界 > 0）：困难子集 NDCG@10 点估计
恰好 **+0.0200**（等于阈值），但 CI 下界 **−0.0003 < 0**，规则要求不满足。

**必须先说清楚：这不是「差一点就通过」。** CI 下界低于 0 的含义是——在这批数据上
**无法排除零效应或负效应**，即**证据不足**。把 −0.0003 表述成「以 0.0003 之差落败」
会诱导读者以为该臂只是运气不好，那是错误的读法。

同时，这个「不通过」的反面也必须记录，否则同样是误导：

1. **第三臂是三条候选路径里唯一在 Recall@5 上显著为正的改动**（全体 +2.86pt、
   困难子集 +5.67pt，CI 下界均 > 0），而封闭门禁里 Recall@5 的门槛是 0.85。
   **但这条只成立于开发集——留出集上它没有复现（见下方「留出集确认」）。**
2. **旧规则的判据与门禁绑定的指标不是同一个**：门禁以 Recall 绑定，规则以 NDCG 裁决，
   所以规则看不见第 1 条的收益。这是规则设计问题，已由 §4.1.1（2026-09-15 修订）
   改为「收益 + 排序非劣 + 成本/SLO + 生成弃答」多目标门禁。
3. 代价是重排条件精度：池覆盖率 0.8714 → 0.9143，条件精度却从 0.877 降到 0.840
   （0.7679 ÷ 0.9143）；排序指标未见改善（R@10 仅 +0.36pt，CI 跨零）。

**三条证据边界（引用本节结论时必须一并引用）：**

- **困难子集是事后定义的。** 其定义是「现役融合臂在 top-10 未命中金标」（141/280），
  且与全体指标出自**同一批 400 条 query**。它是有业务意义的目标子集指标，
  但**不是独立的上线证据**，也不能充当第二次确认。
- **0.9143 是候选池的 oracle 覆盖率。** 生产 Reviewer 只看到最终 evidence，
  覆盖率只说明弃答门禁存在理论空间，**不能证明真实弃答率可达 0.90**。
- **本节全部数字来自同一次分析。** 按 §4.1.1 第五条「禁止追认」，本节任何正向结论
  在取得未参与选型的新留出集数据之前，都不得作为生产采纳依据。该留出集已于
  2026-09-15 一次性消费，结论见下方「留出集确认」——**本节的正向结论没有被复现。**

#### 勘误（2026-09-16 项目方裁定）

**勘误 1 —— 状态。** 本节初稿写「状态维持 `RESEARCH_ACCEPTED / PRODUCTION_NOT_APPROVED`」，
**不成立**：预注册协议规定只有收益门禁与非劣门禁**同时**通过才可进入 `RESEARCH_ACCEPTED`，
而本轮收益门禁未通过。最终状态改为：

```text
CONFIRMATORY_FAIL
PRODUCTION_NOT_APPROVED
SHADOW_NOT_AUTHORIZED
RESEARCH_ARCHIVED
```

**勘误 2 —— 结论口径。** 本节初稿的「本轮既没有证明收益，也没有证明损害」**过于宽泛**。
更准确的结论是：

> **第三臂未证明 Top-5 召回收益。** 但在 **Recall@10、MRR@10、NDCG@10 上通过了预注册
> 非劣门禁**，三项均为正向（+1.52pt / +1.35pt / +1.36pt，LCB 均 > 0），呈现**排序改善**；
> 该改善**主要发生在第 6–10 位**，不足以支持生产采纳。

**勘误 3 —— 「1b 是一条即可通过」是错的。** 本节初稿写「1b 因此是一把刀刃——C1 只要有一条
困难 query 把金标排进 top-5 就能过」。**这个说法不正确。** 1b 的正确读法是
**结构性零基线的「挽救率」端点**（`rescue_rate@5`）：基线恒为 0 是定义使然，但**判据本身
没有因此变松**——在 n = 71 的留出困难集上，用协议 §6 冻结的配对自助（10,000 次、
种子 `20260915`）实测：

| 挽救条数 | `rescue_rate@5` | LCB(0.025) | 1b 判定 |
| ---: | ---: | ---: | :---: |
| 0 | 0.0000 | 0.00000 | ✗ |
| 1 | 0.0141 | **0.00000** | ✗ |
| 2 | 0.0282 | **0.00000** | ✗ |
| 3 | 0.0423 | **0.00000** | ✗ |
| **4** | 0.0563 | **0.01408** | **✓** |
| 5 | 0.0704 | 0.01408 | ✓ |
| 6 | 0.0845 | 0.02817 | ✓ |

**1、2、3 次挽救的 2.5% 分位数都仍然是 0**——一条成功样本在「71 抽 71」的自助重采样中
被整批抽漏的概率是 `(1 − 1/71)^71 = 0.3653`。**需要至少 4 次挽救，置信下界才稳定高于 0。**

**本轮实际挽救数为 0。** 因此 1b 不是被刀刃判据误伤，而是**在任何合理统计方法下
（配对自助、精确二项检验或其他）都确实拿不到 Top-5 收益证据**。

这是我的协议设计错误——错在**基线的命名与解释不准确**（它应当叫 `rescue_rate@5`，
并配一个**有业务意义的最低挽救率**，而不是复用 R@5 的「CI 下界 > 0」外壳），
**不是判据本身有缺陷**。

**这个 FAIL 由两条独立理由共同支撑，不能只归咎于协议。**
第二，**门禁一 1a 独立于 1b，且同样不通过**：它是全体 330 条上的干净判据，
Δ = +0.0000、LCB = −0.0091。**即使把 1b 整个删除，本轮的确认性收益门禁仍然失败。**

#### 决策：本候选的确认性验证正式关闭（2026-09-16 项目方裁定）

**不新建协议版本，也不另外采集数据重跑同一个候选臂。** 理由：

1. 1b 虽然基线恒为 0，但它本质上仍是有效的「失败查询 Top-5 挽救率」检验，
   只是**当前的名称与解释不够准确**；
2. 留出集上的实际结果是 71 条困难查询中 **Top-5 挽救数为 0**。无论改用配对自助、
   精确二项检验还是其他合理方法，**都无法从 0 次挽救中得到 Recall@5 收益证据**；
3. 独立于 1b 的全体门禁 1a 同样得到 Δ = 0、区间跨零。**即使删除 1b，收益门禁仍然失败**；
4. 为同一个**已经确认失败**的候选臂不断换新数据重试，会形成**可选停止（optional
   stopping）与重复抽样**问题，损害预注册验证的可信度。

按协议 §9.3、§9.4，**不得把该 FAIL 事后改写为 `INCONCLUSIVE`**，也不得用开发集数字覆盖它；
按 §9.5，协议本身的问题不得就地修正——**冻结协议与其 sha256 保持不变**，本次只在其外部
追加勘误（本小节与本目录归档说明）。

**将来只有出现下列任一条件，才值得建立新协议与新留出集：**

1. 新候选在**开发集**上已表现出明确的 **Top-5** 改善，而非只改善第 6–10 位；
2. 引入新的检索信号、训练过的融合器或改进的重排器，构成**实质不同**的候选系统；
3. 获得**自然产生**的新专家标注或真实生产查询数据。

**未来协议的修订方向（不适用于本候选）：** 把 1b 明确定义为 `rescue_rate@5` 并设定
**具有业务意义的最低挽救率**；困难集最好按**与系统输出无关**的属性（查询长度、故障码、
产品实体、跨语言等）**预先划分**，而不是按现役系统的失败事后定义。

**生产侧：继续保持现役两路配置，不做任何变更。**
归档：`evaluation/reports/phase4_holdout_prereg_2026-09-15.{json,md}`、
`evaluation/experiments/phase4_holdout_prereg_2026-09-15/`、
`evaluation/experiments/phase4_third_arm_2026-09-15/`。

R@10 −0.0214 [ −0.0643, +0.0179 ]；三路池 NDCG@10 +0.0271 [ −0.0045, +0.0583 ]、
R@10 −0.0179 [ −0.0572, +0.0214 ]。**四个区间全部跨零。**

读法：这是一条稳定的**取舍**，不是提升。新重排器在**排序质量**上一致更好
（MRR@10 +3.3pt / +4.1pt，NDCG@10 +2.0pt / +2.7pt，点估计在两个池上都为正），
而在**召回**上一致更差（R@10 −2.1pt / −1.8pt，点估计在两个池上都为负）。机制是它把
更多置信度压在已选中的头部文档上，挤掉了本可进入 top-10 的其他金标。

两点必须同时说明，否则对比不公平：

- **挑战者拿到的是更宽裕的输入窗口**：`max_length=1024`，而生产重排器在代理脚本里是
  `max_length=512`。即挑战者在更有利的设置下仍然输掉召回。
- 三路池那一行用的是 §3.3 已作废的嵌套构造；重排器 A/B 在同一池内比较仍然成立，
  但该行不代表生产口径下的池。

**结论：不采纳。** 对以召回为绑定约束的封闭门禁而言，「用召回换排序质量」是反向的。

#### 复算口径的可靠性

`mxbai` 与 `gte` 的结果都来自离线复算（临时运行器在报告阶段因不可答 query 的空金标
除零而退出，分数矩阵已落盘）。复算只用 280 条可答 query，与发布报告同口径。矩阵与
池子对齐的判据：形状均为 (400, depth)；文档列表复现已记录的池覆盖率；**用生产重排器
矩阵复算得到 R@5 0.6821 / R@10 0.7357 / R@20 0.7786 / MRR@10 0.5614 / NDCG@10 0.6036，
与 §3.2 已独立核验的「depth-100 + 纯重排」逐位一致**。§3.3 的真实三臂实验把这两个
锚点写成了脚本断言，运行不通过即中止。

### 3.5 重排器概率存在精确并列，纯重排臂因此依赖并列规则

测量层发现，记录备查：RRF 分数是 `1/(60+rank)` 的和，取值高度量化，
**400/400 条 query 的 top-100 窗口内都存在精确并列**（20,164 篇文档落在并列组内，
最大并列组 3 篇）。影响分两处：

| 现象 | 实测 |
| --- | --- |
| 并列跨越 depth-30 边界（决定**已发布协议**的候选**集合**） | **68/400 条 query** |
| 并列跨越 depth-100 边界（决定生产重排窗口集合） | 0/400 |
| 重排器在一个窗口内返回**重复概率**（float32 精度下精确相等） | 298/400 条 query |
| 融合分精确并列 | 5/400；其中并列组内 RRF 分数不同的：0 |

含义：**已发布协议**（top-30 池 + 纯重排）的候选集合，对 17% 的 query 由并列规则
决定；而**纯重排臂**在 298/400 条 query 上存在由并列规则决定的名次。
代理脚本按 `doc_id` 字典序破并列，那是约定而非生产事实。

**生产形态（融合臂）不受此影响**：融合分把 RRF 并列交给重排分去分开，
而融合分自身几乎不并列（5/400，且无实质影响），depth-100 边界的集合也与并列无关。
这是生产配置相对纯重排的一个额外稳健性优势。

## 4. 弃答门禁的可达性：天花板就是池覆盖率

§4.1 要求 impossible 拒答率 ≥ 0.90 且 answerable 答案率 ≥ 0.90。
用本代理集实测的候选池，考察「一个完美的答案存在性检测器能到什么水平」：

| 信号（在 30 池上） | 校准阈值 | answerable 答案率 | impossible 拒答率 | 平衡准确率 | ROC-AUC |
| --- | --- | --- | --- | --- | --- |
| top-1 重排分（现实现） | 0.9984 | 0.3333 | 0.7800 | 0.5567 | 0.6106 |
| top1−top2 间隔 | 0.0025 | 0.6917 | 0.3200 | 0.5058 | 0.5040 |
| top-5 均分 | 0.6220 | 0.9542 | 0.0900 | 0.5221 | 0.5291 |
| 高于 0.9 的条数 | 1.0000 | 0.9292 | 0.1500 | 0.5396 | 0.5175 |
| **金标是否在池内（oracle，不可部署）** | — | 0.8167 | **1.0000** | **0.9083** | **0.9083** |

要点：

1. 可部署的检索分信号里，**没有一个**能同时达到 0.90/0.90——它们的最佳工作点要么
   过度弃答、要么过度作答。这不是阈值没调好：best-case 平衡准确率只有 0.6017。
2. 即使是 oracle「金标是否在池内」，held-out 答案率也只有 **0.8167**，
   因为 30 池覆盖率只有 0.7929。**门禁的上限由覆盖率决定，与门禁实现无关。**
3. 因此该门禁在 depth-100 两路池（覆盖率 0.8714）下**依然不可达**；三路真实等权池把
   覆盖率抬到 0.9143，**理论余量仅 0.0143**——但这是**池覆盖率的 oracle 上限**，
   不是生产可实现值：生产 Reviewer 只看到最终 evidence，因此它只说明门禁存在理论空间，
   **不能用来预测真实弃答率**。

这是一个值得项目方知情的**规则冲突**，且实测把冲突的两端都量化了。

- 旧 §4.1 的**采纳规则**按困难子集 **NDCG@10** 裁决：第三臂点估计 +0.0200（等于阈值），
  CI 下界 −0.0003 < 0，即**证据不足**（不是「差一点通过」），故当时不采纳。
- §4.1 的**弃答门禁**在代理集上不适用（`applicable: false`）；若强行按覆盖率读，
  两路池 0.8714 < 0.90 不可达，三路池 0.9143 才有 0.0143 的理论余量——
  但那是 oracle 池上限，不是生产可实现值。
- 同一实验里，第三臂对 **Recall@5** 的改善在**开发集**上是显著的（全体 +2.86pt、
  困难子集 +5.67pt，CI 下界 > 0），而 Recall@5 恰是封闭门禁绑定的指标之一（门槛 0.85）。
  **该改善没有在留出集上复现**（§3.3）。

换言之：第三臂在「弃答门禁理论可达性」与「封闭门禁绑定的 Recall@5」两处都是正向的，
但在排序指标上证据不足。**项目方 2026-09-15 裁定**：不简单改成 Recall@5 单指标
（那等于用同一批数据追认），改为「收益 + 排序非劣 + 成本/SLO + 生成弃答」多目标门禁
（`docs/PHASE4_EVALUATION_BASELINE_V1_2.md` §4.1.1）。

**该多目标门禁已于 2026-09-15 以预注册形式施加、并在留出集上判定 `FAIL`（§3.3）。**
**项目方 2026-09-16 进一步裁定：本候选的确认性验证正式关闭，不进入 shadow，**
最终状态为 `CONFIRMATORY_FAIL / PRODUCTION_NOT_APPROVED / SHADOW_NOT_AUTHORIZED /
RESEARCH_ARCHIVED`；生产继续保持现役两路配置。

另需澄清：生产并不使用检索分阈值来弃答，而是由 Reviewer 的语义 ABSTAIN 决策。
因此上表的失败**不构成生产拒绝能力的缺陷**，它只说明「用检索分做弃答」这条代理路径不可行。
