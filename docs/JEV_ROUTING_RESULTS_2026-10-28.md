# Jev 路由对照结果：2026-10-28

OpenRouter 上的 Jev 已完成全部 212 条真实路由调用。它在本轮新增语义探针上明显优于
既有规则，但在既有契约上存在退步，并增加约一秒的网络调用延迟。建议保留现有生产
规则，将 Jev 作为后续语义路由候选。本轮到对照实验为止，没有修改生产路由或运行下游流程。

## 正确数与适用边界

| 数据 | 原规则 | Jev | Jev 相对规则改善 / 退步 |
| --- | ---: | ---: | ---: |
| 既有回归集 | 107/107（100%） | 106/107（99.1%） | 0 / 1 |
| 既有困难集 | 36/41（87.8%） | 35/41（85.4%） | 4 / 5 |
| 新增语义探针 | 30/64（46.9%） | 64/64（100%） | 34 / 0 |

困难集细分：32 条契约样例，规则 32/32、Jev 30/32；9 条边界样例，规则 4/9、Jev 5/9。
回归集与原规则共同演进，不能独立证明规则的泛化能力。新增探针由助手编写、未经人工
复核，且与 Jev 提示采用相同语义定义，不能把 64/64 写成生产准确率或独立盲测成绩。
不同数据的预期定义存在差异，因此不以一个合并准确率作为替换依据。

具体行为值得分开看：

- Jev 正确把“查询工单 2 的状态，并查找 VPN 操作手册”识别为复合流程；原规则误判为
  知识查询。对“如何处理？”和“该怎么办？”也正确选择复杂流程。
- “工单 2”没有指定要查什么，既有契约要求复杂流程，Jev 却给出数据查询。
  “How do I fix a VPN MFA failure after changing phones?” 原预期为故障诊断，Jev 选择知识查询。
- “What HTTP status does the API gateway return when a client is rate limited?” 被 Jev
  选择为知识查询，违反原有复杂流程契约。这反映了知识查询范围仍需明确。
- “不要删除工单 2，只告诉我怎么处理”等否定句，以及询问删除/关闭流程的文档请求，
  Jev 与部分旧边界标签不同。本轮提示明确区分提及操作与真正执行操作；这些差异需要
  产品语义裁决，不能一概称为模型能力退步，也不能事后改标签消除错误。

按各集合既定标签，将复杂/不支持请求误分到快速路径的数量：回归集规则 0/56、Jev 1/56；
困难集两者均 4/39；新探针规则 5/32、Jev 0/32。这是入口标签风险指标，不代表实际发生了
越权执行；本轮没有运行下游动作。旧边界定义差异也会影响该指标。

| 指标 | 原规则 | Jev / OpenRouter |

延迟是本机进程墙钟测量，Jev 包含网络往返及响应记录、校验开销，不代表模型纯推理耗时。
单并发、每条一次，尚未测试负载能力或延迟稳定性。

212 个响应的 `usage.cost` 合计 **0.006630792 美元**，按预算规划汇率 6.67 折算
**0.04423 元人民币，约 4.4 分钱**。总输入 157876 token，输出 12218 token。
这是供应商逐次返回的费用，已与平台账户用量核对一致；不含充值和换汇手续费，人民币
金额不是实时汇率账单。运行后立即查询的账户汇总尚未更新完整，约 78 秒后再次查询，
账户用量已为 **0.006630792 美元**，与 212 份响应合计一致；该密钥 1 美元限额剩余
**0.993369208 美元**。保留[首次查询](../evaluation/experiments/jev_router_2026-10-28/run_20261028T062828Z_89823e/account-usage-check.json)
和[最终核对](../evaluation/experiments/jev_router_2026-10-28/run_20261028T062828Z_89823e/account-usage-check-final.json)。

原 TypeSafe 直连失败仍在共享账本保留 **0.002752512 美元**未知预留，它不是已确认扣款。
已知费用加未知预留合计 **0.009383304 美元，约 0.06259 元**，低于 0.70 美元总预算。
全过程共 213 次付费接口尝试：直连失败 1 次、OpenRouter 成功 212 次。

按本批平均输入长度、同价格和无重试估算，路由 1000 次约 0.21 元，10000 次约 2.09 元。
这只是新增路由成本；原规则本身免费，本实验没有测量或证明端到端业务降本。

## 后续选择与简历表述

不建议全量用 Jev 替换原规则。优先人工裁定否定句、文档请求和通用知识问答的路由契约，
再用独立、人工复核的真实样例验证。若继续探索，可考虑保留明确规则与操作约束，只对
语义不明确的请求调用 Jev；需要单独评测这种混合方案，尤其是规则自信但判断错误的情况。
本轮没有实现混合路由，也没有根据这批结果挑选置信度阈值。

本阶段可据实写为：

> 构建规则路由与 Jev 决策模型的可复现对照评测，覆盖 212 条回归、困难及语义探针；
> 实现版本校验、标签隔离、预算预留、故障停止与逐例费用审计，并量化准确性、误路由风险
> 及 P50/P95 延迟，为生产路由选型提供依据。

不建议写成“已上线 Jev”“生产准确率 100%”或“已证明业务降本”。新增语义探针的结果
可作为探索证据，需同时说明其来源和未复核限制。
