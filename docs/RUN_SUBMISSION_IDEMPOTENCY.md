# 普通任务提交的幂等契约

`POST /v1/servicemind/runs` 支持可选的 `Idempotency-Key`，用于客户端超时重试时复用同一个
Agent 任务。Webhook 和受控业务写入的幂等机制继续独立存在。

## HTTP 行为

```http
POST /v1/servicemind/runs
Authorization: Bearer <access-token>
Idempotency-Key: 6f33461f-a63f-4e48-9d70-8e4455b3fc80
Content-Type: application/json

{"ticket_id":42,"goal":"分析该工单的 VPN 故障原因","request_write":false}
```

- 键为 1 到 128 个可见 ASCII 字符，不能包含空白、控制字符或非 ASCII 字符；非法键返回 422。
  UUID 是推荐格式。大小写、标点和双引号按原样参与匹配；服务器不自动去掉引号。
- 命名空间为租户、请求者用户 ID、幂等键。不同租户或不同用户的相同键互不复用。
- 指纹使用已校验的 `ticket_id`、`goal`、`request_write`；JSON 字段顺序不影响结果，
  省略的 `request_write` 与显式 `false` 等价。`goal` 的空白或文字变化视为不同请求。
- 同键同指纹返回 202 与原任务编号；响应中的任务状态可以随运行变化，不缓存整个 HTTP 响应字节。
- 同键不同指纹返回 409，不创建新任务。
- 重试先查已接受的任务，再检查队列容量。因此租户队列满时，原请求仍可重放，新请求返回 429。
- 每次提交仍要求 analyst 角色。重放前根据当前身份执行运行访问检查，权限收窄时返回 404，
  不泄露原任务结果。幂等键不是访问凭据。
- 不传键时保留原有创建行为，重复提交会被视为不同任务。

前端应为一次用户提交意图生成键，并在未确认结果的网络重试中继续使用该键。
用户修改请求或明确开始新任务时生成新键，不要把同一键长期用于不同请求。
内置运行表单已实现这一契约，同时限制重复点击；浏览器端键的存续范围见
[前端说明](../frontend/README.md)。

## 持久化与执行

迁移 `0017_run_submission_idempotency` 创建 `run_submissions`，包含请求指纹和任务引用，
并启用及强制执行 PostgreSQL 行级租户隔离。唯一约束为 `(tenant_id, user_id, idempotency_key)`。

同一命名空间通过事务 advisory lock 串行处理；任务、首条 `run.created` 事件和重试记录
在同一事务中提交。容量拒绝、事件序列化错误或事务失败不会留下孤立记录。
数据库唯一约束还为持久化层提供最后一道重复记录保护。

记录目前没有时间 TTL，随其任务保留；删除任务时通过外键级联删除幂等记录。
因此任务被明确删除后，同一键可以创建新任务。未来若增加清理策略，需要同时公布重试保留窗口。

在 `worker` 模式中，提交后的 PENDING 任务由持久 Worker 领取，响应丢失不会让重试创建第二份任务。
在兼容的 `in_process` 模式中，仅首次提交安排 BackgroundTasks；重试不会再安排一次执行。
旧模式仍有“事务已提交但 API 尚未启动后台任务就退出”的交接窗口，由已有启动恢复处理；
要求持续故障接管的部署应启用独立 Worker。

这项功能保证被接受请求的任务身份去重，不保证外部模型或工具请求恰好发送一次；
崩溃恢复和业务写入继续遵守 Worker、审批及业务幂等契约。

## 验证与对照

`test_run_submission_api.py` 覆盖 HTTP 键校验、参数冲突、权限收窄、角色撤销和仅首次安排后台任务。
`test_run_submission_postgres.py` 使用真实 PostgreSQL 和非超级用户应用角色，覆盖：

- 100 个并发同键 HTTP 请求只创建一个任务、一条初始事件和一条重试记录。
- 相同容量和请求负载下，不传键产生 100 个任务，传同一键产生 1 个任务；两组均返回 202。
- 应用提交完成后模拟响应丢失，重试仍取得同一任务编号。
- 跨租户、跨用户隔离，以及不带应用租户谓词时的数据库 RLS 行过滤。
- 初始事件失败后任务和记录全部回滚，容量拒绝不留下记录，满队列仍能重放原请求。

上述比较使用相同业务载荷的模拟提交，没有模型调用，也没有把去重比率当作生产流量的实际节费比例。
真实节费取决于重复请求发生率、执行阶段与外部服务收费。
