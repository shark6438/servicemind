# 后端简历能力补齐结果（2026-11-05）

本轮完成此前复审最优先的两项：普通任务提交幂等，以及独立 Worker 的容量与故障对照。
新增模型调用和服务商费用均为零。完整验证记录见
[backend_resume_validation_2026-11-05.json](../evaluation/reports/backend_resume_validation_2026-11-05.json)。

## 1. 普通任务提交幂等

`POST /v1/servicemind/runs` 新增可选 `Idempotency-Key`，以租户、用户和键组成命名空间。
同键同请求返回原任务，同键不同内容返回 409；读取重放任务前再次检查当前权限。
任务、首条事件及请求回执在同一 PostgreSQL 事务内写入，租户队列满仍允许原请求重放。
只有首次创建才安排兼容模式的后台执行。

迁移 `0017_run_submission_idempotency` 新增启用 FORCE RLS 的 `run_submissions`。
前端提交表单已发送请求键，网络失败重试复用原键，请求内容变化时生成新键；
同步提交锁避免同一事件循环内的重复点击，成功导航期间也保持锁定。
请求键保存在当前表单内存，重新打开表单代表新的提交意图。

相同请求体、100 个并发请求、同样的 200 条容量配置，真实 PostgreSQL 对照为：

| 请求方式 | HTTP 请求数 | 创建任务数 | 状态 |
| --- | ---: | ---: | --- |
| 无请求键，对应原有创建行为 | 100 | 100 | 全部 202 |
| 相同请求键 | 100 | 1 | 全部 202 |

另验证了响应在提交后丢失、当前权限收窄、角色撤销、跨租户和跨用户隔离、事务回滚及参数冲突。
这是刻意重复请求的正确性对照，不能据此宣称生产费用减少 99%。
详细契约见 [RUN_SUBMISSION_IDEMPOTENCY.md](RUN_SUBMISSION_IDEMPOTENCY.md)。

## 2. Worker 容量对照

在同一主机和隔离 PostgreSQL 上运行真实 HTTP 接口、RunWorker、RunQueue 与受限应用角色。
鉴权替换为测试主体，图执行体替换为 250 ms 模拟模型等待、两次 50 ms 工具等待及一个数据库效果。
两组各在 20 秒内提交 240 个请求，入站速率均为每秒 12 个；每个 Worker 并发为 2。
双 Worker 同时将总执行槽由 2 增至 4，不能解释为相同资源消耗下的加速。

最终结果：

| 指标 | 1 个 Worker | 2 个 Worker |
| --- | ---: | ---: |
| 接受 / 完成任务 | 240 / 240 | 240 / 240 |
| 整组吞吐 | 4.588 任务/秒 | 9.326 任务/秒 |
| 排队 P95 | 30.525 秒 | 5.096 秒 |
| API 返回 202 响应头 P95 | 20.115 ms | 18.410 ms |
| 最后提交后的积压排空时间 | 32.389 秒 | 5.815 秒 |
| 重复执行尝试 | 0 | 0 |

整组吞吐为首次提交至最后完成的任务数除以耗时，双 Worker 是单 Worker 的约 **2.03 倍**。
负载高于处理能力时会形成排队；这里用固定压力观察扩容及排空，排队值不是正常生产请求的延迟。
API 准入时间只计到响应头，不包括 Agent 执行或整个响应体传输。

规范采用的原始记录为
[run_20261105T152630Z](../evaluation/experiments/worker_capacity_v1/run_20261105T152630Z/report.json)，
共保存 514 条 HTTP 请求、各任务时间、逐秒积压、冻结计划和源码哈希。
两组容量阶段共 480 个任务，其余请求用于租户与故障场景。
主机具有 48 个可用逻辑 CPU；短时合成负载不代表真实模型、GLPI 或长期生产容量。

## 3. 隔离与故障观测

- 两个 Worker、每租户并发上限 1，在一个租户突发 24 个任务、另一个租户分时提交 8 个任务时，
  两个租户观测并发均未超过 1；分时租户排队 P95 为 78.974 ms。
  该场景没有正常租户独占控制组，不能声称突发流量完全没有影响。
- API 进程被 SIGKILL 并重启期间，已经开始的任务由独立 Worker 完成，执行一次、效果一次。
  本次 API 恢复可用耗时 12.865 秒，含新进程导入与启动成本。
- 持有任务的 Worker 被 SIGKILL 后，存活者在约 2.993 秒重新开始该任务，约 5.121 秒后完成；
  记录两次尝试、一个数据库效果。测试租约为 3 秒，不能当作默认 120 秒配置的恢复承诺。

故障注入位于数据库效果之前；图执行体已替换，因此该实验不验证外部写入后的故障窗口，
也不证明真实 LangGraph checkpoint 恢复或外部系统恰好执行一次。
方法、限制与复现命令见 [WORKER_CAPACITY_BENCHMARK_V1.md](WORKER_CAPACITY_BENCHMARK_V1.md)。

修复之后先完成一轮探索记录，但当时全仓测试同时运行；为消除这项已知测量干扰，
在其他本地检查全部结束后，以相同计划和源码重新运行最终对照。
两轮计划逐字相同，最终选择依据是测量隔离条件，未据结果挑选更好的一轮。
探索、失败与最终记录均保留；最终五项正确性判据全部通过，源码哈希无漂移。

## 5. 简历可直接使用

建议在原有 Agent 编排和 Jev 路由条目之后新增或合并一条：

> **异步任务与后端可靠性：** 基于 PostgreSQL 持久队列、租约心跳及跨进程执行锁构建独立 Worker，
> 实现租户并发与积压控制、请求幂等和故障接管；100 个并发同键提交仅创建 1 个任务，
> 固定合成负载下单/双 Worker 吞吐由 4.59 增至 9.33 任务/秒，排队 P95 由 30.53 降至 5.10 秒。

若简历空间较少，可用：

> **异步执行与可靠性：** 实现独立 Worker、PostgreSQL 租约与租户额度，支持请求幂等及进程故障接管；
> 100 个并发同键请求创建单一任务，合成负载双 Worker 吞吐达到单 Worker 的 2.03 倍。

面试时应能说明：请求幂等与外部副作用幂等的区别；租约之外为何仍需执行锁；
队列满为什么允许重放；排队与 API 准入时间如何区分；合成吞吐不能直接代表模型生产吞吐。
SQL 索引、游标分页、SSE 与 OpenTelemetry 可以放入工具治理或评测条目作为补充。
如果使用本轮新增成果，项目时间应覆盖 2026 年 11 月，或标注“至今”。
