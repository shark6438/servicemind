## B01 · Python 对象和数据库里的行，为什么不是一回事？（MUST KNOW；源码定点复审）

### 总：先看“同一次工作”里的不同对象

先只考虑 Acme 的 Ticket #5：**用户希望 ServiceMind 分析“VPN 登录失败”**。同一个工单可以产生一份模型分析、一个 Graph 中间结果、一条数据库 Run 记录以及一些事件日志。这些对象彼此关联，但不是同一个东西。

用一句话记住：**Pydantic/Domain 定义业务数据长什么样；Graph State 保存执行过程中的数据；ORM 把需要持久保留的业务记录映射到数据库表。**

| 名称                  | 本块必须掌握的定义                                           | Ticket #5 对应的对象                                    | 是否自动写入 `agent_runs`？              |
| --------------------- | ------------------------------------------------------------ | ------------------------------------------------------- | ---------------------------------------- |
| **Domain / Pydantic** | 校验业务数据的字段和约束；定义了类，不代表有 SQL 表          | `AnalysisResult`、`Evidence`、`ActionIntent`            | 否                                       |
| **Graph State**       | 工作流节点之间传递的键值状态；`Phase3State` 在源码中是 `TypedDict` | `state["analysis_result"]`                              | 否                                       |
| **Checkpoint**        | 当配置了 Saver 时，LangGraph 保存的 Graph State 执行快照     | Ticket #5 的线程状态                                    | 不等于 `agent_runs` 表                   |
| **ORM Row**           | SQLAlchemy 类映射到一张数据库表                              | `AgentRun → agent_runs`                                 | 通过 Repository + Session/事务写入       |
| **Event / Audit**     | 独立记录发生过哪些事件、谁做了什么                           | `RunEvent → run_events`；`AuditEvent → audit_events`    | 否，分别落到自己的表                     |
| **Sink**              | 接收统计/审计数据并决定是否写入的适配器                      | `PostgresContextArtifactSink`、`PostgresModelAuditSink` | 自身不是表；是否产生记录取决于调用及配置 |

**这张表是按职责分类，不是互斥的继承体系。** 例如 `RunEvent` 和 `AuditEvent` 从技术实现上也都是 ORM 类，只不过在业务上承担“历史流水/审计”的角色。`Phase3State` 是 `TypedDict(total=False)`：它用于标注字典结构，**不会像 Pydantic 那样自动进行运行时字段校验**；真正需要严格校验时，代码必须显式调用相应模型的 `model_validate()`。

注意：`src/servicemind/domain/models.py` 与 `src/servicemind/persistence/models.py` **名字相同、层次不同**。前者定义 `ActionIntent` 等业务模型，后者定义 `ActionIntentRecord`、`AgentRun` 等 ORM 表映射。不要只记 `models.py` 文件名。

**为什么说它是完整对象？** 上面列出了 `AnalysisResult` 在冻结源码中定义的全部 18 个字段，包括有默认值的 `proposed_actions/status/claims/alternatives/unresolved_questions/validation_feedback`；`claims` 还包含了 `AnalysisClaim` 的完整字段。它满足模型的**字段和格式契约**，但不意味着已通过 Reviewer 的语义审查。特别是 `proposed_actions=[]` 与本例的只读分析相符。

现在看它经历的三个位置。对象结构保持不变，但外层载体不同：

```text
① AnalysisAgent.run() 得到 AnalysisResult （Pydantic）
      ↓ result.model_dump(mode="json")
② Graph 节点更新 Phase3State["analysis_result"]（dict）
      ↓ finalize_node 组装 result["analysis"]
③ ServiceMindRepository.update_run(..., result=result)
      ↓ tenant_session 中的 UPDATE + 事务完成
   PostgreSQL agent_runs.result（JSON 列）
```

**第二个位置**，源码 `analysis_node` 实际写入：

```python
update = {
    "task_plan": plan.model_dump(mode="json", by_alias=True),
    "analysis_result": result.model_dump(mode="json"),
    "review_result": {},
    # 这里省略控制与轨迹字段，仅展示关键写入
}
```

此时 `state["analysis_result"]` 是**上方完整 JSON 所对应的字典**，并不是只有 `reasoning_summary` 两个字段，也不是新的 SQL 表。

**第三个位置**，当工作流确实走到 `finalize_node` 时，源码的关键操作是：

```python
result = {
    "analysis": state.get("analysis_result"),
    # 真实 result 还有 evidence/review/task_plan/trajectory 等字段
}
await repository(state).update_run(
    UUID(state["run_id"]), status, result=result, error=error
)
```

最终 `agent_runs` 数据库行的**少量字段投影**可能如下（只展示这些字段，不冒充完整表行或完整 `result`）：

```json
{
  "id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "status": "succeeded",
  "result": {
    "analysis": {
      "classification": "network/vpn",
      "reasoning_summary": "工单记载 VPN 登录失败，建议先核对认证及网络连接情况",
      "evidence_refs": ["ev-f7fe417f1c910cc6"]

```

**不要误读：** 上方 `status="succeeded"` 只是“本教学案例假定正常完成”的状态示例。真实 Run 也可能失败、终止或先等待审查；`result.analysis` 可能为空、缺失或被另一条路由跳过。`result.analysis` 在真实写入时是上方 `AnalysisResult` 的完整字典，而不止投影出的三个字段。**也不代表调用 `model_dump()` 后数据库已写入**。

### 关键设计：为什么不为每个 Python 业务模型建一张表？

核心原因是**生命周期不同**。`AnalysisResult` 和 `TaskPlan` 是工作流中间产物，会随节点重新计算；Graph State 承载它们，条件满足时 Checkpointer 保存工作流快照。`AgentRun` 则承担跨 HTTP 请求的身份、状态、最终结果查询，因此 `agent_runs` 有独立行。`RunEvent` / `AuditEvent` 为了回答“发生过什么”，也各自有表；Context/Model Audit Sink 则承担另一类条件性观测记录。

源码没有一张 `analysis_results` ORM 表。出现一个 `AnalysisResult`，**不能推出**数据库新增一行 `analysis_results`；只有 `finalize_node → update_run` 的真正代码路径，才支持“这个分析进入 Run 的 `result` JSON”的结论。

### 必要失败边界：对象产生 ≠ 已落盘

- `model_dump(mode="json")` 只是序列化；它不写 PostgreSQL。
- `Phase3State` 是 `TypedDict` 状态定义，不等于 PostgreSQL ORM；Checkpoint 是由配置的 LangGraph Saver 管理的**另一套持久化机制**，不能把 `state` 的字段认作 `agent_runs` 的列。
- `ServiceMindRepository.update_run()` 在 `tenant_session` 的 SQLAlchemy 事务中查询并修改 ORM 行，只有事务完成后才可以把变更视为已成功提交；代码存在不代表本轮运行已执行。
- 不能假定所有 Run 必须走 `analysis_node` 或 `finalize_node` 的同一正常路径；若节点提前失败、快路由结束或运行被中断，数据形状和持久化结果可能不同。

## B02 · 一次 AgentRun 从创建到结束，实际经历什么？（MUST KNOW）

### 总：`agent_runs` 是“任务记录”，不是任务全部细节

Ticket #5 的 AgentRun 是一次工作执行的**持久身份**。同一张 Ticket 可以存在多次 Run，每次有自己的 `run.id`、`thread_id`、发起用户、目标、状态、最终结果。Ticket ID 与 Run ID 不相同。

### 正常流程：人工发起只读分析

人工调用 `POST /v1/servicemind/runs`，要求分析 Ticket #5：

```json
{"ticket_id":5,"goal":"分析 VPN 登录失败并给出排查建议","request_write":false}
```

在 `api.py` 中校验 `analyst` 权限后：

```python
run = await repository.create_run(
    user_id=context.user_id,
    ticket_id=request.ticket_id,
    goal=request.goal,
    request_write=request.request_write,
)
await repository.append_event(run.id, "run.created", {...})
background_tasks.add_task(_process_webhook_run, run, context)
```

这里的 `{...}` 是教学省略写法；源码确切 payload 只有 `ticket_id` 与 `request_write`。**先创建 ORM 行，后单独写事件**；不是把两个 Repository 调用误说成同一事务。

`create_run` 建立一条 `AgentRun`，初始化状态 `pending`。下面是它作为**ORM 行的主要字段投影**（并非 HTTP API 响应原样）：

```json
{
  "id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "tenant_id":"11111111-1111-4111-8111-111111111111",
  "user_id":"analyst-acme",
```

> [!NOTE] 为什么称为“投影”？
> 这是根据 `AgentRun` 字段契约手工填充的**虚构数据**。真实 `id/thread_id/created_at` 由代码/数据库产生，不能声称和这里的固定 UUID、时间一致。

### 状态如何改变？

`RunStatus` 的有效枚举为：`pending`、`running`、`waiting_approval`、`waiting_review`、`succeeded`、`failed`、`cancelled`。这描述**可能的状态集合**，不是必须按此顺序逐一经过。示例只读 Run 常见流程可概括为：

```text
pending → running → succeeded
                   └→ failed（可能失败）
```

如果开启需要审批的写请求，则有条件进入 `waiting_approval`；若触发人工审查分支，可以进入 `waiting_review`。某些状态不能从任意状态随意取消：API 的 `:cancel` 路由目前只允许 `pending / waiting_approval / waiting_review`。

**真实读取**：`GET /runs/{run_id}` 通过 `get_run` 查询主行，并另外查询当前 ActionIntent；读到 `status=succeeded` 只能说明主 Run 已更新为这个状态，**不是证明某条 GLPI 跟进实际写入**。

### 关键设计：为什么 `create_run()` 返回 ID，却不等待 AI 处理完？

Run 的身份需要先持久化，后续 HTTP 轮询、事件订阅、恢复才有可查锚点。请求返回 HTTP `202` 与 AgentRun 已完成属于两个不同判断。

### 必要失败边界

- 人工创建和 Webhook 接收并非同一入口：Webhook 使用 `claim_webhook_run` 把幂等收据与新 Run 放在一条事务中；参见 B06。
- `AgentRun.status` 是可更新列；它不是**全部状态转移规则本身**。转移是否合法还要看调用方 API、Graph 控制与审批路径，不能仅凭 ORM StrEnum 承诺一个全局有限状态机校验器。
- 异常终结时 `error` 可能被填充，但不能推断所有失败路径都保证留下相同格式；这取决于是否到达 `update_run`。

## B03 · Run 执行中的 TaskPlan、Graph State 和 Checkpoint 是怎么关联的？（MUST KNOW）

### 总：三个名字指向不同层次

在一次复杂流程里，Supervisor 可能决定：先让 Data Agent 读取 Ticket，再让 Knowledge Agent 找手册，再 Analysis，再 Reviewer。

- **`TaskPlan`**：任务设计，写着有哪些 `Task`、谁依赖谁、预算和截止时间。
- **`Phase3State`**：本次 Graph 的“工作台”，包括任务计划、已拿到的 Evidence、分析结果、审查结果和控制权。
- **Checkpoint**：把 Graph 工作台状态保存起来，以便在需要时恢复；这由 **LangGraph checkpointer** 负责，并不是 `agent_runs` 表上的新增列。

### Checkpoint 怎样接线？

冻结源码中的 `src/service/service.py:lifespan()` 使用 `initialize_database()` 得到 `saver`，调用 `configure_supervisor_checkpointer(saver)`；而 `supervisor_graph` 在 `build_supervisor_graph()` 中由 LangGraph `StateGraph` 编译。`start_run` 用 `run.thread_id` 构造 config，再 `supervisor_graph.ainvoke(...)`。

**因此：** `agent_runs` 是 ServiceMind 的业务 ORM；`Phase3State` 在图内更新；Saver 的内部 checkpoint 存储由另外一套接口负责。它们相关联，但你不能在 `persistence/models.py` 里寻找 `task_plan` 表来解释图恢复。

### 关键设计：为什么不每执行一个节点就更新 `agent_runs.result`？

Graph State 在多个节点间频繁变化，保存为检查点可以保留运行中的上下文。`agent_runs` 负责跨请求查询、终结摘要、状态；如果把每个中间细节都塞成一个不断改写的业务行，会混淆执行态与总账。

### 必要失败边界

- **有数据库 Run 不必然有 Checkpoint**：崩溃如果发生在记录 Run 后、Graph 开始前，恢复代码可能找不到快照。
- **有 Checkpoint 不等于权限可无条件恢复**：`resolve_resume_scope()` 会复核已记录的身份范围，并且存在范围收缩后无效化证据、撤回待审批动作的流程。
- **恢复不是凭空重放原 HTTP**：源码区分存在快照时恢复和没有快照时重新启动。恢复候选由 `list_recoverable_runs()` 过滤，现有查询包括 `pending/running/waiting_approval`，不包含 `waiting_review`；不能据此断言所有类型的人工审查都自动恢复。

## B04 · RunEvent 和 AuditEvent 有什么区别？（MUST KNOW）

### 总：状态是结果，事件是过程

`AgentRun.status="succeeded"` 只能告诉你“现在成功了”；它不能告诉你为什么路由到了 Knowledge、何时发生审查、有没有经过撤回。因此有 `run_events`。

另一方面，安全意义上的操作还可能需要 `audit_events`：是谁授权、撤销或操作了哪个对象。**事件流水与审计流水不是同一张表**。

### 正常流程：同一个 Ticket #5 的两种记录

**RunEvent**（来自 `run_events`，字段示例为 ORM 行的投影）：

```json
{
  "tenant_id":"11111111-1111-4111-8111-111111111111",
  "run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "sequence":2,
  "event_type":"evidence.joined",
  "payload":{"count":2,"gathered":2,"dropped":0},
  "created_at":"2026-10-10T09:01:00Z"
}
```

真实 `evidence.joined` 的 payload 还携带 `evidence_refs`；这里是字段投影。

**AuditEvent**（独立表；例如用户取消 Run 时实际会调用 `repository.audit()`）：

```json
{
  "tenant_id":"11111111-1111-4111-8111-111111111111",
  "run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "actor_id":"analyst-acme",
  "event_type":"run.cancelled",
  "resource_type":"AgentRun",
  "resource_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "payload":{}
}
```

**这两条是分开的教学案例**：一个展示 `evidence.joined`，另一个展示取消事件，不要误以为一次正常成功 Run 同时发生了取消。

### 事件序号是怎么来的？

`ServiceMindRepository.append_event()` 先对对应 AgentRun 行 `SELECT ... FOR UPDATE`，再计算当前 `RunEvent.sequence` 最大值 +1，写入新行。`run_events` 数据表还有 `UNIQUE(run_id,sequence)`。

为什么这样设计？两次并发写事件时，不能都写成 `sequence=3`。对父 Run 行加锁提供同 Run 的串行写入条件，而不是只在 Python 里 `len(events)+1`。

### 关键设计：append-only 不等于普通日志文件

`audit_events` 在迁移 `0003_append_only_audit` 中安装了阻止 `UPDATE/DELETE` 的触发器；与 `run_events` 的“按序插入”不能混为同一个物理保证。**`run_events` 的顺序性来自加锁与唯一约束；`audit_events` 的不可变性另有数据库触发器。**

### 必要失败边界

- `RunEvent` 没有把所有 Graph State 字段自动复制进 `payload`。需要诊断时应区分：主行、Graph 快照、事件、审计日志。
- `create_run()` 与之后的 `append_event()` 分成独立的 Repository 事务，不能虚报“两者必定同时提交”。如果中间失败，可能出现已创建主行而缺首个事件，需要恢复/排错机制识别。
- 事件流读取 `list_events(run_id,after)` 以序号过滤，而不是依据 wall-clock 时间排序；跨 Run 不能把 `sequence=3` 解释成全平台第三件事。

## B05 · 分析结果怎样变成“可审批但尚未执行”的 Action？（MUST KNOW）

### 总：建议、意图、审批、实际执行是四件事

员工的 Ticket #5 可能需要记录内部跟进说明。Analysis Agent 认为：“已检查 VPN/MFA，建议记录排查建议。”**它给出建议，不等于它已经写入 GLPI。**

M8 学到的 Handoff 是监督者将经过 Reviewer 审查的行动上下文转交给 Action Agent；M9 关心交接之后**产生了什么对象、在哪里保存、怎样变成审批记录，以及是否真的产生了外部副作用**。

### 正常流程：一次明确要求写入的人工请求

> [!WARNING] 与 M7 Webhook 不同
> Webhook 新建 Run 的 `request_write` 在 `claim_webhook_run()` 中固定为 `False`，不能直接沿它来演示审批写操作。因此下面沿用 Ticket #5，但换成**授权分析员主动提交 `request_write=True` 的另一条教学 Run**。这不是同一次只读 Webhook Run。
> **ID 必须分开**：前面只读 Run 的教学 ID 是 `aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa`；本块和 B05A、B12 使用的独立写 Run 是 `99999999-9999-4999-8999-999999999999`。它们共享同一张 Ticket #5，但不是同一次执行。

```text
人工请求 request_write=True
      ↓
AnalysisResult（提出 bounded proposed_actions）
      ↓
Reviewer ReviewResult=PASSED（需审查条件满足）
      ↓
HandoffEnvelope（仅允许 append_ticket_followup）
      ↓
ActionAgent.propose_from_handoff() → ActionIntent（领域对象）
      ↓
ServiceMindRepository.save_action_intent()
      ↓
action_intents（ORM 行 status=proposed）
      ↓
人类 Approver 的审批准入与 decision
      ↓
approvals（ORM 行） + action_intents.status 更新
      ↓
审批通过时产生 tool_outbox 记录；后续执行另走受控链
```

**第 1 个对象：`ActionIntent` 是什么形状？** 下方是**完整的 v2 领域对象数据形状**。本教学固定：Review 决定为 `passed`，`ReviewResult.feedback="工单事实具有证据支持，可形成私有跟进提案"`，`evidence_refs` 只有 Ticket #5 那条证据。随后采用冻结源码的 `stable_digest()` 和 `ActionIntent.calculate_hash()` 计算下方三个 **真实、可复算的 SHA-256 十六进制摘要**：

```json
{
  "id": null,
  "run_id": "99999999-9999-4999-8999-999999999999",
  "action_type": "append_ticket_followup",
  "target_id": 5,
  "arguments": {
```

**不要把审批的三种结果混为一谈。** `record_approval()` 对正常的 `approved` 和 `rejected` 决定都会先把数据库 `agent_runs.status` 从 `waiting_approval` 变为 `running`，让 Graph 有机会恢复；但随后分支完全不同：

| 人工点击时的情形                  | `action_intents` / `approvals` 的变化                        | Graph 后续流向                                               | 通常最终 Run 结果                            |
| --------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | -------------------------------------------- |
| **正常批准 `approved`**           | 保存 Approval，Action → `approved`；同事务写 `action.approved` Outbox | `approval → execute → finalize`，执行前还要权限和工具安全核验 | 取决于执行结果，不等于点击后立即成功         |
| **正常拒绝 `rejected`**           | 保存 Approval，Action → `rejected`；**不创建批准 Outbox**    | `decline_run() → approval → finalize`，**不返回 Supervisor 重新派生** | `cancelled`（Graph 的 `finalize_node` 路径） |
| **权限收窄令旧动作作废 `voided`** | **不记录对旧动作的批准或拒绝**；原 `proposed` 动作撤回并留 Audit | `approval:voided → supervisor`，重收集、重算；将来如产生新动作需重新审批 | 这时尚不固定为最终态                         |

以 Ticket #5 为例，假如审批人选择 `rejected`，一次典型对象投影是：

```json
{
  "approval": {"action_intent_id":"dddddddd-dddd-4ddd-8ddd-dddddddddddd","decision":"rejected"},
  "action_intent_status": "rejected",
  "run_status_after_record_approval": "running",
  "graph_next": "finalize",
  "run_status_after_finalize": "cancelled",
  "tool_outbox_action_approved_created": false
}
```

> [!NOTE] 这段是多对象**组合投影**，并非真实存在的单张表。`run_status_after_record_approval` 是瞬时中间状态；`finalize` 按 `approval.decision == rejected` 将 Run 归为 `cancelled`。`decline_run` 只接受拒绝，不需为不执行写操作而强制再次联系权限服务，但仍要核对原 Run Checkpoint 身份。参考：[repository.py L371–437](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/persistence/repository.py#L371-L437)；[api.py L329–420](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/api.py#L329-L420)；[supervisor_workflow.py L1611–1634](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/orchestration/supervisor_workflow.py#L1611-L1634)；[supervisor_workflow.py L1725–1750](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/orchestration/supervisor_workflow.py#L1725-L1750)。


### 关键设计：为什么还需要 ActionIntent 哈希？

`ActionIntent.calculate_hash()` 对 action 类型、目标、参数以及 v2 安全上下文做规范化后计算 SHA-256。它防止“先审查一种写入，后执行时悄悄把正文换成另一种”。`approval` API 还要求 `expected_action_hash`，形成意图与审批对象绑定。**签了什么，要执行的就应该是什么**。

`action_intents.run_id` 是唯一键：一个 Run 在任一时刻保留一个待审批 Action slot。当前动作在权限收缩后可能被标记 `withdrawn`；随后新的不同 Intent 可以复用原 slot（删除旧已撤回行，再创建新行），但只应在对应的 Audit 记录保存了撤回历史后解释该过程。

### 必要失败边界

- `ReviewResult` 不是 `PASSED`、`request_write=False` 或没有 ready Action Task，不能合法交接给 Action。
- `Approval.action_intent_id` 唯一；重复同一决定返回旧记录；冲突决定报错，不能将一次批准和拒绝同时写入。
- `save_action_intent` 使用事务级 Advisory Lock 防止并发不同 Intent 抢同一个 Run 的 slot；同 action_hash 可复用记录，非撤回的不同 hash 拒绝。
- ActionIntent/Approval 已落库 ≠ 工具已经执行。真正写 GLPI 还要经过后续受控执行、输出验证及权限复核。

## B05A · 等待审批时权限被撤销，旧对象为什么不能继续使用？（MUST KNOW）

### 总：失去读取权限，等于失去“继续使用先前结论”的资格

B05 已经认识了三件不同的事：**批准、拒绝、旧动作作废**。这一块只解决第三种情况。M8 的 Evidence、Analysis、Review 不是互不相关的文本：Analysis 是根据 Evidence 推出的结论，Review 审查的是那份结论，Handoff 和 ActionIntent 又依赖已审查的结论。**只要上游 Evidence 因权限变化不能再使用，后续这些对象也不能原样保留。**

最简单的现实类比：分析员原本有权查看公司 VPN 网关日志，用这些日志写了一份处理建议；审批等待期间，他失去了网关日志的访问权。此时不能只把“重新查询日志”的权限改小，却继续使用旧日志形成的审核结论去执行写操作。

### 正常流程与最小例子：Acme Ticket #5 的同一 Run

假设人工分析员 `analyst-acme` 在 `run_id=99999999-9999-4999-8999-999999999999` 中请求 `request_write=true`。**暂停审批时**，Checkpoint 中记录的权限包括 `analyst` 角色、GLPI Entity `1`、Groups `7` 和 `9`；曾收集三条 Evidence，Review 通过，并已建立待审 ActionIntent。

**步骤 1：恢复前，先读 Run 自己的原始身份，而不是审批人的更大权限。** `runtime._recorded_principal()` 从原 Run Checkpoint 恢复用户、角色、Entity、Group；审批人的 TenantContext 只提供必须一致的租户，不能把审批人的 Groups 加给原请求者。

```json
{
  "checkpoint_recorded_principal": {
    "tenant_id": "11111111-1111-4111-8111-111111111111",
    "user_id": "analyst-acme",
    "roles": ["analyst"],
    "allowed_glpi_entity_ids": [1],
    "group_ids": [7, 9]
  },
  "current_provider_answer": {
    "established": true,
    "roles": ["analyst"],
    "entity_ids": [1],
    "group_ids": [9]
  }
}
```

这是**权限数据的教学投影**，不是 `ResumeScope` 直接 `model_dump()` 的结果（`ResumeScope` 实际是 frozen dataclass）。

**步骤 2：求交集，只能收窄不能扩大。** `resolve_resume_scope()` 从身份服务重新核验，在写请求场景使用 `fresh=run.request_write`，因此示例写请求要求新鲜验证。结果 `effective.groups=[9]`，比 recorded 少了 Group `7`，所以 `narrowed=true`。若 Checkpoint 当时有待审批 `action_intent`，`void=true`。

```json
{
  "recorded_groups": [7, 9],
  "effective_groups": [9],
  "narrowed": true,
  "resume_scope_void": true,
  "outcome": "此处由身份核验结果决定，教学示例不伪造实际枚举"
}
```

**步骤 3：作废 Evidence 和六项派生产物。** 构造的 `scope.update` 对 Graph State 的修改可以看成下面的**字段投影**：

```json
{
  "roles": ["analyst"],
  "allowed_glpi_entity_ids": [1],
  "group_ids": [9],
  "data_evidence": null,
  "knowledge_evidence": null,
  "evidence_dirty": false,
  "joined_evidence": {},
  "analysis_result": {},
  "review_result": {},
  "handoff_envelope": {},
  "action_intent": {},
  "human_review": {},
  "task_plan": "原 TaskPlan 经 dispatcher.invalidate() 后的完整 JSON",
  "plan_revision": "原 plan_revision + 1"
}
```

这段是**组合投影**：`task_plan` 与 `plan_revision` 用文字说明动态计算结果，并非能够直接传入 Graph 的有效 `Phase3State` 字典。真正的 `_DERIVED_PRODUCTS` 列表**恰好是六项**（见下表）；新旧 Evidence 的值变为 `None`，是给 `_reset_or_append` reducer 的**清空指令**，最终保存为 `[]`，不是让 Graph 的证据字段永远等于 `null`。

| 原来已有的对象                        | 权限收窄后的处理                   | 为什么不能保留                           |
| ------------------------------------- | ---------------------------------- | ---------------------------------------- |
| `data_evidence`、`knowledge_evidence` | 传 `None` 给 reducer，清空已有证据 | 原查询是在更大的访问范围内执行的         |
| `joined_evidence`                     | 写 `{}`                            | 合并结果依赖被撤销的证据                 |
| `analysis_result`                     | 写 `{}`                            | 分析结论不能继续引用失权证据             |
| `review_result`                       | 写 `{}`                            | 之前的审查不覆盖新证据范围               |
| `handoff_envelope`                    | 写 `{}`                            | 旧交接的审查摘要与证据摘要不再适用       |
| `action_intent`                       | 写 `{}`                            | 旧写提案不能在新权限下复用               |
| `human_review`                        | 写 `{}`                            | 人工审核记录不能作为新派生对象的授权凭证 |

**步骤 4：重新打开 TaskPlan。** 如果只是清空结果而保留任务 `SUCCESS`，Supervisor 会误认为工作已经完成，所以 `TaskDispatcher.invalidate()` 会把计划里的任务重置为 `PENDING`、清空 `output_ref`，但**保留 `attempts` 历史次数**。举例（两个 Task 的投影）：

```json
{
  "before": [
    {"task_id":"T1","status":"success","output_ref":"ev-f7fe417f1c910cc6","attempts":1},
    {"task_id":"T3","status":"success","output_ref":"analysis_result","attempts":1}
  ],
  "after": [
    {"task_id":"T1","status":"pending","output_ref":null,"attempts":1},
    {"task_id":"T3","status":"pending","output_ref":null,"attempts":1}
  ]
}
```

**步骤 5：Graph State 作废和 SQL 待审 Action 撤回是两回事。** `resume_run()` 会在重启 Graph 前调用 `_withdraw_pending_action()`：Repository 只能撤回状态为 `proposed` 的 ActionIntentRecord；然后 Runtime **分别**写 `audit_events` 的 `action.withdrawn` 与 `run_events` 的同名事件。注意这些写入与 `withdraw_action_intent()` **不是一个横跨三次调用的共同 SQL 事务**。稍后 `save_action_intent()` 如需持久化不同的新动作，在确认旧状态为 `withdrawn` 后，可删除旧行、复用唯一 Run slot；撤回历史应在此前写入的 AuditEvent 中保留。

```json
{
  "action_intents_row_before": {"id":"dddddddd-dddd-4ddd-8ddd-dddddddddddd","status":"proposed"},
  "action_intents_row_after_withdrawal": {"id":"dddddddd-dddd-4ddd-8ddd-dddddddddddd","status":"withdrawn"},
  "audit_events_added": {"event_type":"action.withdrawn","resource_type":"ActionIntent"},
  "run_events_added": {"event_type":"action.withdrawn"},
  "old_approval_created": false,
  "graph_resumed_via": "approval:voided → supervisor"
}
```

上面同样是**跨表组合投影**，不是数据库中某一条 JSON 原样。被撤回的旧 Action 不代表已经执行或已经被人工否决。新 Evidence/新 Analysis/新 Review/新 Action 若重新产生，仍需**新的审批**。

### 关键设计：三种看似相近的分支为何不能混用？

| 情况                               | 应该怎么处理                                                 | 是否留下新 Approval 行      | 是否会重新派生旧证据上的结论          |
| ---------------------------------- | ------------------------------------------------------------ | --------------------------- | ------------------------------------- |
| **身份服务无法建立当前权限**       | `ResumeBlocked`，调用 `_record_block` 写 AuditEvent `run.resume_blocked`，暂停续跑 | **不会**，保持等待态        | **不会**，因当前权限未知              |
| **已确认权限收窄且待审动作仍存在** | 清空旧 Evidence/六产物，重开 TaskPlan，撤回旧提案，发送 `voided` 给 Graph | **不会批准/拒绝旧提案**     | **会**，在收窄后的范围重新收集和计算  |
| **人工明确点“拒绝”**               | `decline_run()`，不需要为了拒绝一个动作强制重新校验身份提供者，但需要原始 Checkpoint 身份 | **会**，记录真实 `rejected` | **不会**，`after_approval → finalize` |

这三个分支的最重要区别是：**“身份不确定”不能当作已验证收窄；“权限导致作废”不能冒充人工拒绝；人工拒绝也不能被解释成同意系统重新提案。**

### 必要失败边界

- `ResumeBlocked` 并非把 Run 自动更新为 `failed`。权限暂不可核时应留下阻塞审计且不消耗人类的批准决定；等权限可证明后才能再续跑。若恢复 Checkpoint 的租户/原身份本身不一致，则 `_recorded_principal()` 抛 `PermissionError`，属于另一类一致性故障。
- `void=true` 的前提是 `narrowed` **且** Checkpoint `action_intent` 为真；没有待审 Action 时，权限收窄仍需要重新派生证据，但不一定存在一条待撤回 SQL Action。
- 即使没有权限收窄，只要存在待审 Action，`step_shortfall()` 仍会检查当前执行所需角色和 Entity。一个从未获得写操作所需角色的用户不能借“权限没变”通过。
- 此处需要清空六个派生产物而非只清空一份数组，避免“旧 Review PASSED 仍允许旧写”的隐式越权。具体历史漏洞与 `_reset_or_append` 的修正放在 A6，不挤入正常教学。
- `decline_run()` 只接受 `rejected`；不能通过构造 `approved` 参数绕过权限复核。最终 Graph `finalize` 在典型拒绝分支下将 Run 记为 `cancelled`，中途 `running` 只是恢复用状态。

### 源码学习：照这条顺序阅读，而不是从四个函数名开始背

## B06 · 重复请求为什么不一定创造重复 Run、重复审批或重复外部动作？（MUST KNOW）

### 总：幂等不是“忽略所有重复消息”

幂等（idempotency）关注：**同一个业务操作被请求多次，最终应当识别为同一次操作，而不是重复发生副作用。** 但不同对象的幂等键、粒度和事务范围都不一样，不能用一个 `idempotency_records` 表解释全项目的所有去重。

### 正常流程 A：Webhook 重复通知，数据库里发生了什么？

假设 Acme 的 GLPI 对**同一已签名 HTTP 投递（相同 `X-GLPI-signature`）**原样重试两次。冻结入口 `receive_glpi_webhook()` 计算 `body_hash=SHA256(raw_body)`、`idempotency_key="glpi-webhook:" + X-GLPI-signature`，再通过 `webhook_run_id(tenant_id,signature)` 得出确定性 UUID；因此**去重粒度是签名一致的投递，而不是所有语义相同的业务事件**。Repository 的 `claim_webhook_run()` 随后在一个 `tenant_session` 事务里做：

1. 向 `idempotency_records` 插入 `(tenant_id,idempotency_key,action_hash)`，`ON CONFLICT DO NOTHING`。
2. 读回收据并加 `FOR UPDATE` 锁，检查旧的 `action_hash` 是否与此次一致。
3. 创建**确定的同一个** `AgentRun.id`，`ON CONFLICT DO NOTHING`。
4. 只有 Run 确实新建成功，才插入 `webhook.accepted` 的第 1 条 `RunEvent`。
5. 关联收据 `result={"run_id":...}`，`completed=True`，事务结束后返回 `(run,duplicate)`。

**输入**（简化）：

```json
{"tenant_id":"11111111-1111-4111-8111-111111111111","idempotency_key":"glpi-webhook:<X-GLPI-signature>","action_hash":"<SHA256(raw HTTP body)>","run_id":"<webhook_run_id(tenant_id, signature) 产生的 UUID>"}
```

**第一次输出**（逻辑投影）：`idempotency_records` 新增一行、`agent_runs` 新增一行、`run_events.sequence=1`；返回 `duplicate=False`。

**第二次签名和请求体均不变**：查询到旧收据、复用同一个 Run，返回 `duplicate=True`；不是再插入第二个 Run。这种能力由**数据库唯一约束+同一事务+冲突分支**共同承担，不是简单写个 `if`。

**必须单独记住的边界**：HMAC 签名覆盖 `body + timestamp`，如果 GLPI 为同一个 Ticket 事件**重建时间戳并重新签名**，签名与幂等键也会改变。冻结入口没有用 GLPI 的业务事件 ID 做二次去重，故不能承诺这种重新签名的同语义事件一定合并为一条 Run。`webhook_run_id()` 的稳定性也是相对于 `(tenant_id,signature)` 而言。

**危险情况**：同一个 `idempotency_key` 被配上另一个 `action_hash`，源码会抛 `RuntimeError`，不应默默复用旧记录。

### 正常流程 B：审批通过时为什么要写 Outbox？

审批通过后，系统既要保存数据库里的审批决定，又希望后续向外部流/工作者发出 `action.approved` 事件。若先提交审批、随后发布消息，进程在两者之间崩溃，消息可能永远丢失。

所以 `record_approval()` 在**同一个数据库事务**内保存：

```text
Approvals 新行
 + ActionIntent.status = approved
 + AgentRun.status = running
 + ToolOutboxRecord(status=pending, event_type=action.approved)
                ↓
          统一事务提交
```

Outbox 行的字段投影：

```json
{
  "tenant_id":"11111111-1111-4111-8111-111111111111",
  "aggregate_type":"ActionIntent",
  "aggregate_id":"dddddddd-dddd-4ddd-8ddd-dddddddddddd",
  "event_type":"action.approved",
  "payload":{"run_id":"99999999-9999-4999-8999-999999999999","action_hash":"<hash>","action_type":"append_ticket_followup"},
  "idempotency_key":"action-approved:<action-id>:<action-hash>",
  "status":"pending",
  "attempts":0
}
```

此后可见的 Outbox 状态是 `pending → leased → published`，或者失败重试又回 `pending`，重试耗尽为 `dead`。**`published` 表示投递记录，不证明 GLPI 操作成功。** 它尤其不能和 MCP task 的 `completed` 混为一谈。

**实际来源**：[api.py L251–270](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/api.py#L251-L270) 计算签名级幂等键；[webhooks.py L30–35](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/harness/webhooks.py#L30-L35) 使用 UUID5 映射 `(tenant_id, signature)`；[webhooks.py L76–98](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/harness/webhooks.py#L76-L98) 的 HMAC 会把时间戳计入签名。因此这里既不能只背 Repository，也不能脱离 HTTP 调用方谈“业务事件恰好一次”。

### 关键设计：三种重复控制必须分开

| 机制                                                         | 管什么                     | 什么算“同一次”                                               |
| ------------------------------------------------------------ | -------------------------- | ------------------------------------------------------------ |
| Webhook claim                                                | 一条重复通知生成的 Run     | `(tenant_id,idempotency_key)`，同时核对 action_hash 和确定 Run ID |
| `ServiceMindRepository.claim_idempotency/complete_idempotency` | 受控副作用账本的认领与完成 | 同租户幂等键，内容 Hash 不许冲突；`completed` 在实际阶段使用 |
| `ToolOutboxRepository.enqueue_in_transaction`                | 审批事件不可丢失的投递请求 | `(tenant_id,idempotency_key)`，同事务写入 pending 事件       |

`action_lock()` 使用 PostgreSQL Advisory Lock 串行化同键副作用；对外部系统的“绝对恰好一次”不能只凭本仓库上述代码静态宣称，需要核对执行器、远端写入与回读验证。

### 必要失败边界

- `ON CONFLICT DO NOTHING` 不是“旧请求一定成功”：必须检查旧记录属于哪个 action_hash，`completed` 和真正结果分别代表不同阶段。
- Outbox 的 `lease_owner/lease_expires_at` 防止一个 worker 随意领取另一 worker 的 lease；`published()`/`failed()` 检查所有权。
- `prune_published()` 会按时间和批量删除已发布 Outbox；`dead` 被保留作未投递的诊断线索；因此 **Outbox 不是无限期的永久审计账本**。
- 对 `AgentRun` 的首个事件，人工 `create_run()` 与独立 `append_event()` 并非同事务；不能把 Webhook 的原子创建性质泛化到所有入口。

## B07 · 一份知识文档从导入到可检索，实际有几种对象？（MUST KNOW + SOURCE DEEP）

### 总：Document 和 Chunk 不是同一个持久化对象

假设 Acme 上传一份“VPN/MFA 排查手册”。用户看到的是一份文档；检索系统还需要把它解析、切成较大的 ParentChunk、再切成用于检索的 ChildChunk。它们分属不同的领域对象和 ORM 表。

| 领域对象（Pydantic）                                      | ORM 表                     | 用途                                     |
| --------------------------------------------------------- | -------------------------- | ---------------------------------------- |
| `KnowledgeDocument`                                       | `knowledge_documents`      | 文档元数据、内容、ACL、来源、索引状态    |
| `ParentChunk`                                             | `knowledge_parent_chunks`  | 给模型显示的较完整段落或结构片段         |
| `ChildChunk`                                              | `knowledge_child_chunks`   | 检索命中的更小片段，指向 parent          |
| `KnowledgeQuery/RetrievalHit/Citation/KnowledgeRAGResult` | **不等于上述四张表**       | 搜索时产生的查询、命中、引用等运行时结构 |
| `KnowledgeIngestionJob`（ORM）                            | `knowledge_ingestion_jobs` | 每租户每数据源的一行“最近摄取状态”登记   |

### 正常流程：同一份手册会产生什么对象？

### 真正的创建/更新顺序

`KnowledgeRepository.replace()` 在同一租户事务中：

1. 对文档按 `(tenant_id,source,source_record_id)` 进行 Upsert；同源重导**保留原 canonical document ID**。
2. 把文档 `index_status` 写成 `pending_index`。
3. 删除这个文档的旧 ChildChunk，再删除旧 ParentChunk；建立新的 Parent 和 Child。
4. 返回使用 canonical ID 归一化的 Document/Chunks，交给后续搜索索引流程。
5. 搜索索引同步完成后，代码有 `mark_indexed` / `reconcile_indexed` 将文档标记 indexed 的路径。

**为什么 `pending_index` 重要？** PostgreSQL 写入成功，不代表 OpenSearch 已经完成索引；两个系统不是同一个事务。一个文档可能“主库有记录，但搜索还不可用”。这里以 PostgreSQL 中的登记状态作为索引发布判断的一部分。

### 文档变化与撤回（不等于删掉所有东西）

- 更新版本：同源新版本覆盖主文档的内容/版本，并替换 Chunk 代，后续索引需要重建或协调。
- 临时停用：`set_document_active(tenant,source_record_id,is_active=False)` 在**文档 ACL 内更改标记**，其返回 `matched/changed`，不是“删除文档行”。调用侧负责同步搜索索引的冗余 ACL 状态；单凭 PostgreSQL 更新不能证明 OpenSearch 已同步。
- 源数据消失：`delete_missing` / `delete_documents` 会删除主文档，关联 Chunk 按外键 CASCADE；搜索索引仍有自己需要协调/清理的生命周期。

### 知识摄取 Job：与文档主行不同

`knowledge_ingestion_jobs` 按 `(tenant_id,source)` 唯一，`begin_ingestion_job()` 如果已经存在则 `attempts += 1`，重置 error/metrics 并进入 `running`；`complete_ingestion_job()` 将其标记 `succeeded` 或 `failed`。**它只保存同源当前状态，不是每次摄取的不可变历史事件流。**

**教学输出**：同一个 `doc-1` 第一次失败、第二次成功，可能最终只看到一行 `status=succeeded,attempts=2`。不能因为状态 succeeded 就断言第一次未曾失败。

### 关键设计：为什么“数据库已有文档”和“搜索能查到”不是同一回事？

这里有**两层持久化对象**：PostgreSQL 中的 `KnowledgeDocumentRecord` 是源数据/ACL/版本的持久权威；OpenSearch 需要另外获得索引投影。`KnowledgeRepository.replace()` 将主库行置为 `pending_index`，表示“准备同步新索引”，而不是“搜索已经发布”。只有索引操作经过相应流程后，`mark_indexed()` 才更新登记。

**最小实例**：运维看到 `knowledge_documents` 中 `source_record_id=doc-1, source_version=v2, index_status=pending_index`，这可以支持“新版本已保存到主库”，**不能**推出“搜索 v2 已经成功”或“ACL 在 OpenSearch 中已同步”。故障定位应继续查看索引流程/查询时段/状态校准。此设计是跨存储生命周期一致性的一部分，而不是数据库事务自动保证两套系统同时提交。

### 必要失败边界

- 文档的 `KnowledgeDocument.validate_hash` 要求正文和 `provenance.content_hash` 一致；不能随便修改正文而保留旧 hash。
- Knowledge ACL 包含租户、实体/群组/个人和生效时窗；“写到本租户表里”不自动意味着每个同租户用户可见。
- `KnowledgeRAGResult.items` 存的是**RAG 域自己的 `domain.knowledge.ContextItem`**，不是 M8 的 `context.contracts.ContextItem`，两者虽然同名，生命周期不同。
- 检索 Hit、Citation、索引副本与主数据库 Document 是四类对象；不能把它们合成“知识库的一张表”。

### 状态和版本有什么区别？

**版本**：同一个 `(tenant,scope,memory_type,subject_key)` 的内容可能改变。新的内容可以创建 `version=2`，保留相同 `lineage_id`，再根据策略决定 `quarantine/active/...`；旧版本可能 `superseded`。如果完全相同的活跃内容再次被提交，源码也存在“返回旧行而不新建版本”的去重路径。

**状态**：当前某一版本是否生效。冻结 `MemoryStatus` 六种值：`candidate`、`quarantine`、`active`、`superseded`、`revoked`、`expired`。**它们是可用状态集合，不是一条规定了必须从 candidate 依次走到 expired 的单一路线。**

**事件**：谁、何时、为何改变了它。例如：

```json
{
  "memory_id":"<当前 memory UUID>",
  "actor_id":"approver-acme",
  "event_type":"memory.active",
  "reason_codes":["HUMAN_REVIEW_PASSED"],
  "payload":{"reviewed_version":2,"reviewed_content_hash":"<hash>"},
  "run_id":null,
  "trace_id":null
}
```

这同样是**字段投影**。人工异步审查可以没有 `run_id`；由某个 Run 导致的撤回则可写对应 Run ID。`memory_events` 的存在，是为了让“修改长期记忆”可以留下可追溯历史，而不只看当前 `memory_records.status`。

**这份示例为什么能说“对应源码产物”？** `Phase5Governance.post_run()` 会把一个经确认的终态 Run 提炼为 `MemoryCandidate`：`subject_key="ticket:5:verified_outcome"`，`content` 为按键排序的分析摘要 JSON，`source_trace_id` 取 Graph `thread_id`，`created_by="post-run-memory-middleware"`，`expires_at` 为生成时刻加 90 天，租户级 Episode 的 `provenance` 还带实体/群组 ACL。此处时间是教学固定时钟；实际运行应由 `datetime.now(UTC)` 决定。对应 `phase5_governance.py L736–832`。

### 哪些调用链真的存在？

`Phase5Governance.post_run()` 是从完成的 Run 中提取候选并提交治理的一种入口；`MemoryRepository` 有内存版和 Postgres 版，`Phase5Governance` 默认使用 `PostgresMemoryRepository` 工厂。冻结配置 `SERVICEMIND_MEMORY_ENABLED=False` 是**默认值**，真实部署是否改开关未知。

`PostgresMemoryRepository.persist()` 在租户事务内，先处理过期、申请写锁及“同一 subject”的 Advisory Lock，再按幂等键或最近版本判断创建、复用、隔离。`transition()` 会做状态校验、活动版本互斥和 MemoryEvent 记录。

### 关键设计：MemoryRecord 不是“LangGraph Store 里的所有长期记忆”

`service.py:lifespan()` 另外调用 `initialize_store()` 给底层 Agent `agent.store` 注入 LangGraph Store。**这与 ServiceMind 自建的 `memory_records` ORM + `PostgresMemoryRepository` 是不同的接口和存储模型**。不能看到都叫 memory 就认为只有一套表，也不能说 `initialize_store()` 直接创建了 `memory_records`。

### 必要失败边界

- 激活 procedural memory 还有额外来源核验/人工审查要求；不能因为普通 episodic candidate 能存，就假设 procedure 可自动 active。
- `MemoryRecordRow.provenance/taint_labels` 在当前 ORM 是 JSONB，读侧使用 JSONB 表达式；这是实际数据库读边界，不是随意 JSON 字符串。
- 撤回与过期可能由不同 Actor/维护路径产生；`memory_events.run_id` 允许 `NULL`，不是审计缺口的证明。
- “存在 Postgres Repository 类”不等于该部署 Memory 功能已经启用、真的写过记录。

## B09 · Context、模型调用和工具审计，为何“代码有、数据库可能没有”？（MUST KNOW + SOURCE DEEP）

### 总：记录存在，要同时满足创建条件和 Sink 接线

M8 说过：`ContextEnvelope` 可以决定模型实际看到什么。M9 接着问：**这个 Envelope 自己会像 AgentRun 一样全部保存到 `agent_runs` 吗？**

答案：不会。ServiceMind 把**部分上下文选择元数据**通过 `PostgresContextArtifactSink` 保存到独立的 `context_artifacts`，而不是把整个完整 Prompt 复制一份到主表。另有 `model_invocations` 记录模型调用统计，`tool_policy_decisions` 等记录工具治理。

### 正常流程与最小例子：三种审计 Sink 的具体输入与输出

**A. Context Sink**：输入是一次 `ContextEnvelope`，输出是 `ContextArtifactRecord`。

```json

  "run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "task_id":"T3",
  "agent_role":"analysis",

    {"item_id":"ev-f7fe417f1c910cc6","source":"evidence","decision":"selected","reason":"ranked_within_budget","tokens":100,"content_hash":"<64位摘要>"}

  "tokens_used":100,
  "redaction_count":0

```

这是**ContextArtifact ORM 行投影**：没有原始工单全文，也没有完整 `ContextEnvelope.items`；但 `selection_manifest` **确实包括条目 ID 和内容 Hash**，不能谎称它完全不含可关联标识。`tokens_used=100` 是示例值，不是默认 tokenizer 实测。

**C. Tool Policy + Invocation 审计**：在 Tool Platform 路径中，允许调用某工具是一份 `ToolPolicyDecisionRecord`，真正尝试执行后的结果另存 `GovernedToolInvocationRecord`。**允许≠已调用；已调用≠验证成功**。

### 真正的 feature gate 是什么？

冻结 `core/settings.py` 的默认值：

| 设置                                      | 冻结默认 | 影响                                                         |
| ----------------------------------------- | -------- | ------------------------------------------------------------ |
| `SERVICEMIND_CONTEXT_ENABLED`             | `False`  | `Phase5Governance.build_context()`/fast context 直接返回 None，不产出相应 ContextArtifact |
| `SERVICEMIND_MODEL_GATEWAY_AUDIT_ENABLED` | `False`  | `ConfiguredModelAuditSink` 不把模型调用写入 Postgres（另有 tenant/DB 条件） |
| `SERVICEMIND_MEMORY_ENABLED`              | `False`  | 长期记忆的治理路径默认不自动开启                             |
| `SERVICEMIND_RAG_ENABLED`                 | `False`  | 企业 RAG 检索路径默认不启用；知识摄取表是否已有文档是另一个问题，不能据此断言表为空或导入代码不会被调用 |
| `SERVICEMIND_TOOL_PLATFORM_ENABLED`       | `False`  | 工具平台网关、MCP Task 装配是条件性的                        |

`SERVICEMIND_RAG_ENABLED` 的作用边界也要分清：关闭是**当前查询是否走企业 RAG**的条件，不能直接推断 `knowledge_documents` 曾经是否被导入过；要查入库对象须追 `KnowledgeRepository.replace()` 与实际 ingestion。参见 [settings.py L195–201](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/core/settings.py#L195-L201)、[repository.py L79–189](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/rag/repository.py#L79-L189)。

因此，数据库中没有上述记录，**不能仅凭这一点断言“Agent 没跑/没调用模型/没有工具行为”**；先检查对应开关、实际入口和 Sink 是否 wired。反过来，有 ORM 模型类，也不能当作线上真的已经积累了记录。

### 关键设计：“只写 Sink”究竟是什么意思？

`ContextArtifactSink.record(envelope)` 的接口主要写入选择结果，业务 Agent 不靠重新读取这张表来完成当前分析。`ModelAuditSink` 也主要留下模型调用统计。这类对象更接近**观测/审计投影**，不是 Run 的控制状态本身。

但这里不能把**所有审计表**一概称为“永远只写”：`PostgresToolAuditSink.verify_receipt()` 会**读取** `governed_tool_invocations` 的已成功/已验证 output_hash 来核验 MCP receipt。能否读到数据取决于具体消费者代码，而不是对象名有 `Audit`。

### 必要失败边界

- `context_artifacts` 及 `model_invocations` 在治理迁移里设置了 tenant RLS 和阻断更新删除的触发器；并不是所有 22 表都 append-only。
- `ConfiguredModelAuditSink` 的开关只控制**持久化审计**，不能据此说 Model Gateway 本身未被调用；两者不是同一功能。
- `ContextArtifactRecord` 保存的是**选材台账**，不是“模型一定接收了这些字段的运行时全量证明”；模型调用是否完成，还需要模型调用/Run 记录关联核验。

## B10 · 工具调用、Outbox、MCP Task 为什么是三个不同的对象？（SOURCE DEEP）

### 总：一件“调用 GLPI 工具”的事，至少分为三种状态

1. **授权判断**：这个用户/Agent 是否有权调用这一个工具？（Tool Policy Decision）
2. **工具执行**：真实工具有没有执行、调用返回什么、输出是否经过校验？（Governed Tool Invocation）
3. **异步任务/可靠投递**：如果需要跨进程、跨请求或者异步完成，怎么追踪？（MCP Task / Outbox）

它们不是同一条记录反复改名，也不保证每个 Run 都用上三套。冻结 `SERVICEMIND_TOOL_PLATFORM_ENABLED=False`，因此**实际启用与否需部署核验**。

### 正常流程：同一个读工具从允许到完成

假设 Agent 读取 Ticket #5 的信息。工具请求对象 `ToolCall` 中会有 `request_id/run_id/task_id/user_id/tenant_id/tool_name/arguments` 等字段。下面两张是**ORM 行的关键字段投影**。

授权决定示例：

```json
{
  "decision_id":"<policy decision UUID>",
  "request_id":"<tool request UUID>",
  "run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "tool_name":"glpi.read.ticket",
  "allow":true,
  "requires_approval":false,
  "reason_codes":[],
  "argument_hash":"<64位哈希>"
}
```

执行结果审计示例：

```json
{
  "request_id":"<tool request UUID>",
  "run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "tool_name":"glpi.read.ticket",
  "status":"succeeded",
  "verified":true,
  "attempts":1,
  "output_hash":"<64位哈希>",
  "policy_decision_id":"<policy decision UUID>"
}
```

`tool_policy_decisions` 按 `(tenant_id,decision_id)` 唯一，`governed_tool_invocations` 按 `(tenant_id,request_id)` 唯一。**这两个唯一键不同；一次 policy decision 不能等同于一次已成功执行。**

### MCP Task：异步工作对象的状态

当平台使用 MCP Tasks 扩展时，`McpTaskRecord` 可保存：

```json
{
  "tenant_id":"11111111-1111-4111-8111-111111111111",
  "task_id":"<MCP任务UUID>",
  "request_id":"<工具请求UUID>",
  "run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "workflow_task_id":"T1",
  "tool_name":"glpi.read.ticket",
  "argument_hash":"<64位摘要>",
  "status":"working",
  "output_ciphertext":null,
  "output_hash":null,
  "cancellation_requested":false,
  "lease_owner":"worker-1",
  "lease_expires_at":"2026-10-10T09:05:00Z"
}
```

它以 `(tenant_id,task_id)` 和 `(tenant_id,request_id)` 各自唯一，状态允许 `working/completed/failed/cancelled`。完成时只存**输出密文**和 Hash；复原结果需要有合法的解密能力，不能把“表里有 output_ciphertext”理解成“明文写入表里”。

`PostgresMcpTaskStore` 实现 `create/get/heartbeat/finish/cancel/recover_interrupted`，还会对过期/失效任务处理；但这只是类的能力。其装配在 `service.py:lifespan` 里受 `SERVICEMIND_TOOL_PLATFORM_ENABLED` 和数据库类型影响，测试中的内存实现也不能被误认为每个生产环境都用。

### Outbox 与 MCP Task 的区别

| 对象                           | 重点问题                                | 主要状态                             | 由谁管理                |
| ------------------------------ | --------------------------------------- | ------------------------------------ | ----------------------- |
| `ToolOutboxRecord`             | “审批事件可靠地送到下一个通道了吗？”    | `pending/leased/published/dead`      | `ToolOutboxRepository`  |
| `McpTaskRecord`                | “某个 MCP 异步工具任务现在做到哪一步？” | `working/completed/failed/cancelled` | `PostgresMcpTaskStore`  |
| `GovernedToolInvocationRecord` | “这一次工具调用是否执行并验证？”        | `succeeded/failed/denied/cancelled`  | `PostgresToolAuditSink` |

**不要记成“published→completed→succeeded 是同一张表的顺序”**：它们是不同对象，不能直接拼成一个通用状态机。

### 关键设计：身份、哈希与外部副作用的最后分界

`ToolGateway` 在对外执行之前有工具注册、schema、capability、角色/实体/污点、policy 与审计等检查。只有拿到合法的调用条件，才会交给具体 Provider。`ActionAgent.propose_from_handoff()` 本身从来不拿 GLPI 凭据，也不直接执行副作用；`ToolGateway`/受控执行器才属于真正的外部调用边界。

### 必要失败边界

- `Policy allow=True` 不是已调用；`status=succeeded` 也要结合 `verified` 判断是否满足验证要求。
- MCP Task 的 `lease_owner/lease_expires_at` 是控制谁可合法完成任务的状态，不是给 LLM 的一般知识。
- `ToolOutboxRecord` 成功被发布，不保证 Provider 写入结果；外部副作用仍需核验。
- `tool_invocations` 旧表与 `governed_tool_invocations` 新表同时存在。前者 `ServiceMindRepository.record_tool_invocation()` 写 `tool_name/input_hash/status/result_ref` 等简化字段；后者带 policy/checksum/verified。**名字相近不能合并成一张表**。

## B11 · 为什么 Acme 和 Globex 的 ORM 行不会自然混在一起？（MUST KNOW）

### 总：租户分界是多层协作，不是一句 `WHERE tenant_id=...`

冻结代码的核心概念：`Tenant` 是企业目录行，`TenantMembership` 是设计上的用户/租户成员关系 ORM 表，`GlpiIntegration` 是每个租户的 GLPI 配置，`tenant_session()` 为业务事务绑定 `app.tenant_id`，迁移为需要隔离的表设置 PostgreSQL RLS。

**必须区分“表存在”与“认证入口真用它”**：当前 `OIDCVerifier.verify()` 直接从已验证 JWT 的 `tenant_id/sub/realm_access.roles/glpi_entity_ids/glpi_group_ids` 构造 `TenantContext`，此处**没有查询 `tenant_memberships`**。M9 所查 Seed 只插 `Tenant + GlpiIntegration`，没有 Seed Membership；不能因为表定义存在就声称它在当前 API 身份链已经 wired。参见 [auth.py L108–145](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/security/auth.py#L108-L145) 与 [seed_phase2.py L31–92](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/scripts/seed_phase2.py#L31-L92)。

### 正常流程：Acme 查自己的 Ticket #5 Run

```python
repo = ServiceMindRepository(ACME_TENANT_ID)
run = await repo.get_run(ACME_RUN_ID)
```

Repository 的构造不访问数据库；真正执行 `get_run` 时才打开：

```python
async with tenant_session(self.tenant_id) as session:
    return (await session.execute(select(AgentRun).where(AgentRun.id == run_id))).scalar_one_or_none()
```

`tenant_session()` 在事务内执行：

```sql
SELECT set_config('app.tenant_id', :tenant_id, true)
```

最后的 `true` 是本次事务局部设置；数据库 RLS 规则使用 `current_setting('app.tenant_id', true)`。它保护**被迁移启用该策略的租户表**，不是所有库表天然自动隔离。

**例子**：

```text
请求来自 Acme 的合法身份
→ 取 TenantContext.tenant_id = Acme UUID
→ ServiceMindRepository(Acme UUID)
→ tenant_session 设置本事务 app.tenant_id=Acme
→ 数据库 RLS 过滤 agent_runs
→ 查询 Acme 的 Run ID 才有结果
```

若尝试用 Acme 事务读 Globex 的同名表记录，符合 RLS 的数据库角色下不应直接得到 Globex 的行。**RLS 不负责替 HTTP 请求验证身份**；HTTP/OIDC/Webhook 的租户断言可信性要在前面的身份边界建立。也要注意具备绕过 RLS 能力的数据库超级用户/特殊权限不属于上述隔离承诺。

### 三类租户对象的字段形状

```json
{
  "tenants":{"id":"11111111-1111-4111-8111-111111111111","slug":"acme","name":"Acme"},
  "tenant_memberships":{"tenant_id":"11111111-1111-4111-8111-111111111111","user_id":"analyst-acme","roles":["analyst"]},
  "glpi_integrations":{"tenant_id":"11111111-1111-4111-8111-111111111111","entity_id":1,"enabled":true,"webhook_secret_encrypted":"<Fernet密文>"}
}
```

这只是**三张不同表的关键列投影**。`GlpiIntegration` 同一个租户在 ORM 约束里只有一个 `tenant_id` 唯一行（`UniqueConstraint("tenant_id")`）；密钥是加密存储，不代表所有租户由 RLS 自动分配不同的密码。

### 关键设计：事务结束时到底发生了什么？

`tenant_session()` 使用 `async with session_factory() as session, session.begin(): ...`。成功退出事务上下文时提交；异常时回滚。因此 `session.add()` + `await session.flush()` 不等于“任意后续逻辑失败都不可能回滚”。这一点对 M9 的“对象什么时候真正活在数据库中”尤其重要。

### 必要失败边界

- `global_session()` 用于如租户目录这样的非 RLS 表；不能用它访问租户业务表并以为会自动注入 tenant ID。
- `Tenant` 目录本身不同于其余 tenant-scope 的 21 张 ORM 业务表；迁移 0001、0005、0008、0011 按各自清单设置 RLS。**实际迁移是否应用到目标环境须另验**。
- `GlpiIntegration` 的 Secret 用 Fernet 保护静态凭据；Webhook 的 HMAC 验证是另一层，不是 RLS 的功能。
- API 构造的 `tenant_id`、Graph State 中保存的 `tenant_id`、DB 事务上下文的 `app.tenant_id` 处在不同层次。字段同名并不意味着可以随意信任和互换。

## B12 · 给你一个 Run ID，怎样画出完整对象生命线并排错？（MUST KNOW + SOURCE DEEP）

### 总：一条 Run 的所有对象不是一张大表

现在假设某用户问：“为什么 Ticket #5 的 AI 分析迟迟没有完成？”你拥有的是 Run ID `99999999-9999-4999-8999-999999999999`。

不要立刻猜“模型坏了”或“RAG 没检索到”。从主记录出发，按**是否存在→状态→时间线→Graph State→依赖对象**逐级定位。

### 正常流程与最小例子：一条 Run 的最小排错路径

**① 查 `agent_runs`，先确认 Run 身份和终态。**

```json
{"run_id":"99999999-9999-4999-8999-999999999999","ticket_id":5,"status":"waiting_approval","request_write":true,"error":null}
```

这个投影的意思是“当前主行报告正在等待审批”，**不是模型请求正在运行，也不是审核已经批准**。

**② 查 `run_events`，确认它走了哪些节点。**

```json
[
  {"sequence":1,"event_type":"run.created"},
  {"sequence":2,"event_type":"evidence.joined"},
  {"sequence":3,"event_type":"review.completed"},
  {"sequence":4,"event_type":"control.handoff"}
]
```

这是**教学构造的时间线缩略图**，不代表源码真实运行时只有这四条事件或一定按此相邻顺序出现。真实 Graph 可能追加 `agent.completed`、工具、失败与重规划事件。

**③ 查 Graph Checkpoint**：是否确实停在人工批准中断？`state.handoff_envelope` 与 `state.action_intent` 是否对应同一 Run，Checkpoint 的租户/用户范围是否仍然有效？

**④ 查 `action_intents` 与 `approvals`**：有待审批 Intent 吗？是否已经有一条 Decision？如果已经审批但主 Run 状态仍旧，看审批恢复边界及后台恢复路径。

**⑤ 查 outbox / audit / tool invocation**：只有进入外部动作路径时才需要继续。`outbox.status=published` 只说明投递完成；`ToolInvocation` 的 verified 和最终回读才能讨论写操作实际成功。

**⑥ 查 Context/Model/Memory/Knowledge 附属对象**：仅在该路径涉及这些功能时检查。Context 默认 off，不能因为 `context_artifacts` 缺失就得出“分析模型没收到资料”的结论；Knowledge 的 `pending_index` 也可能导致搜索侧未就绪。

### 一个可执行的 SQL/Repository 检查方向

下面 SQL 用于**概念展示**；查询需要合法数据库权限、合适租户会话和脱敏访问，不能直接在生产超级用户连接中使用而绕开 RLS：

```sql
-- 在已建立并正确绑定租户的数据库事务内：
SELECT id, tenant_id, ticket_id, request_write, status, error
FROM agent_runs
WHERE id = :run_id;

SELECT sequence, event_type, created_at
FROM run_events
WHERE run_id = :run_id
ORDER BY sequence;

SELECT id, action_type, status, action_hash, expires_at
FROM action_intents
WHERE run_id = :run_id;

SELECT action_intent_id, decision, decided_by, decided_at
FROM approvals
WHERE run_id = :run_id;
```

注意 SQL 中 `:run_id` 是**SQLAlchemy 风格命名绑定参数占位符**，不是 psql 可直接粘贴的完整语句。实际排查更优先使用代码内 `ServiceMindRepository` / 被授权 API；不要为了查看而绕过租户权限。

### 对象失效后的排错对照：不要把三条路径当成一次重试

如果 Ticket #5 的 Run 曾经显示 `waiting_approval`，之后审批 UI 又显示 409，先用事件和审计记录定位：是**人拒绝了**、**访问权限缩小导致动作作废**，还是**身份服务暂时不可用**。这三种情况操作上完全不同：

| 查到什么                                                     | 谁写的                                          | 下一步理解                                                   |
| ------------------------------------------------------------ | ----------------------------------------------- | ------------------------------------------------------------ |
| `approvals.decision=rejected`、`action_intents.status=rejected`，Run 最后 `cancelled` | Repository + Graph finalize                     | 人已拒绝，不应自动重算成另一份动作                           |
| `audit_events.event_type=action.withdrawn`、`run_events.event_type=action.withdrawn`，新任务计划重新 `pending` | Runtime scope narrowing + Dispatcher.invalidate | 旧动作因失权被撤回，应看是否已重新收集 Evidence 并产生新提案 |
| `audit_events.event_type=run.resume_blocked`，Run 仍等待，没有新批准行 | `_record_block`                                 | 当前身份无法核实，等待可验证后再续跑，不能误记为已拒绝       |

权限变化详细对象形状、六项清空与 SQL 撤回见 B05A；恢复 API 与 Graph 的关键分支见 [runtime.py L190–309](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/orchestration/runtime.py#L190-L309)、[runtime.py L350–485](https://github.com/shark6438/servicemind/blob/19d9a377fb98e1c3f56edc59be40b374013bc08b/src/servicemind/orchestration/runtime.py#L350-L485)。

### 必要失败边界：不能仅用“表存在”推断谁运行过

- 某表没有记录，可能是功能关闭、业务路径没经过、写入失败或事务回滚；不能统一叫“Bug”。
- 某表有记录，不保证外部系统一致，例如 `knowledge_documents` 有 pending 行不保证 OpenSearch 可查。
- 某条 `run_events` 有 `run.succeeded`，仍应核对主行、执行证据与具体外部动作结果；不能把“工作流成功结束”误等于“每一个可能的副作用都发生”。
- 前文模拟数据不可拿来宣称真实 RUNTIME OBSERVED；完整运行验证需要部署开关、迁移、数据库回读、Checkpoint 和对应测试/事件证据。

```text
  -> if decision=approved: resolve_resume_scope FIRST
       +--> ResumeBlocked -> audit run.resume_blocked; no Approval recorded
       +--> scope narrowed + pending action -> voided -> retract ActionIntent + audit/events
                       -> Graph task dispatcher invalidate -> Supervisor re-derives
       +--> else Repository.record_approval -> approvals + approved action
                          -> agent_runs.status=running + same-tx tool_outbox pending
                          -> resume_run -> execute (subject to final gates)
  -> if decision=rejected: do NOT require fresh entitlement lookup
       -> Repository.record_approval -> approvals + action.status=rejected
                         -> agent_runs.status=running (temporary)
       -> decline_run -> Graph finalize -> agent_runs.status=cancelled
       -> NO action.approved Outbox

RAG ingestion
  -> KnowledgeRepository.replace
       +--> knowledge_documents (upsert, pending_index)
       +--> knowledge_parent_chunks (delete previous, insert current)
       +--> knowledge_child_chunks  (delete previous, insert current)
  -> indexing/reconcile -> mark_indexed (condition: indexing actually succeeded)

Phase5 memory post_run (condition: memory enabled, governance admits)
  -> PostgresMemoryRepository.persist
       +--> memory_records
       +--> memory_events
  -> transition/revoke/expire -> memory_records.status + memory_events

Context model-input governance (condition: context enabled)
  -> PostgresContextArtifactSink.record -> context_artifacts

ConfiguredModelAuditSink (condition: model audit enabled + DB + scoped tenant)
  -> PostgresModelAuditSink.record -> model_invocations

Tool Platform gateway (condition: tool platform enabled/configured)
  -> PostgresToolAuditSink.record_policy -> tool_policy_decisions
  -> PostgresToolAuditSink.record_invocation -> governed_tool_invocations
  -> MCP Task Store (optional adapter) -> mcp_tasks
```

> [!NOTE] 接线不等于部署证据
> 即使 `context_enabled` 在部署中关着，源码条件分支也还是 `WIRED FACT`（带条件）；只有实际记录证明已经运行时才能标 `RUNTIME OBSERVED`。尤其 Outbox 的发布消费者是否在当前部署真正运行，不能凭 `ToolOutboxRepository` 有 `claim()` 就宣布已生效。

### 每个失败场景的学习重点

F01–F05 用来训练你区分 **主对象/事件/Checkpoint/幂等**；F06–F08 训练 **动作意图/人审/可靠通知与真正执行**；F09–F10 训练 **版本化对象与派生索引**；F11–F12 训练 **可观测性开关与已授权≠已执行**。这些是基于冻结代码能推导的失败边界，不是本轮对故障的自动运行复现。

### A7.2 MUST KNOW：闭卷应该讲清楚

1. **对象分类**：区分 Domain（数据契约）、ORM（数据库行）、Graph State/Checkpoint（执行状态）、RunEvent（过程）、AuditEvent（审计）以及条件性 Sink。
